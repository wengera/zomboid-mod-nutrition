# Eat and cook hooks
Verified against 42.20.4 (b0bbce05d5) · 2026-10-01 · scope: where a nutrition mod's hook on the intake or cooking path sits — the side its writes survive on, its seat in the order of writes, what it can still change and the wall it meets; the dispatch is `platform/lua-platform.md`'s, the order of writes and the drink path `facts/eating-pipeline.md`'s, the cook block, the craft split and the evolved dish `facts/cooking-and-recipes.md`'s.

## Rules
<a id="rules"></a>

- Run the mod's intake math where the eat completes: a multiplayer client never reaches the eat action's completion step, so nothing a mod hangs off the client side of that path ever runs [#0109, #0110].
- Never put mod logic in a client-side wrapper of a timed action's completion: the Lua complete is skipped on a client, so the wrapper installs and then stays silent [#2005/C/C-only].
- Keep every write an `OnEat` handler makes on its server arm: the client arm is the packet twin's notification, and the store it would write belongs to the server [#1131/M/n=1, #2061/C/inference].
- Never count on the completion wrapper to see a cancelled eat: a cancel reaches `Eat` through the net action's stop and the eat action's server-stop step, which does not pass through the completion step [#0111, #2064/C/inference].
- Expect no eat-side seat to see a drink from a fluid container: the fluid path has no eat hook and no eat packet, and a container drink from the drink action reaches a mod through a server-side wrapper of the action's `updateEat`, which a direct `DrinkFluid` call and the world-water route bypass [#0084/C/C-only, #1133/M/n=1, #2690/C/C-only, #2827/M/n=1, #2828/C/inference].
- Expect a later mod's non-chaining replacement of a method you wrapped to remove your capture silently: a replaced function value drops the earlier closure, no sentinel can see it, and only your own per-eat counters standing still reveal it — so a wrapper keeps a call counter and the next boot beside a new eat-wrapping mod reads it [#2842/C/inference, #1067/C/snapshot, #2562/C/snapshot, #2817/C/C-only].
- Expect an eat-hook correction to reach the client one push late: the server's eat packet has already left when the hook runs, so the correction rides the next once-a-second player-stats push [#0006, #0114, #2063/C/inference].
- Re-sync a food's remainder after restoring a field the mod lowered before vanilla's part-eat: vanilla's `Eat` sends the lowered value to the eater's client inside the eat, and the client keeps it until the next item-stats packet [#4155/C/inference] [#4147/M/n=1] [#4148/M/n=1] [#4170/M/n=1].
- Write a `ReplaceOnCooked` item's cooked nutrition into the replacement's script, never into a cook hook on the item it replaces: the cook block swaps the item and returns before it sets the cooked flag or calls the hook [#0266, #0257, #2067/C/inference].
- Name a script hook's target as a global function or a function one level inside a global table, never a local or a deeper path: the eat path resolves the script's name through the Lua manager's function-object lookup, which walks a dotted name through global tables and never finds a local, and the cook path looks a dotted name up exactly two levels, so a bare global or a one-level table member resolves on every path and a deeper path resolves only on the eat path [#3501/C/C-only, #3502/C/C-only].
- Define that global in a `shared/` file and branch on the side inside it: the folder decides nothing, and the eat hook fires on both sides [#0922/M/n=1, #1031/M/n=1].
- Nil-check `isServer` and `isClient` before the protected call that reads them: a protected call on a nil comes back as a failure that names nothing, which turns absence into an error string instead of a branch [#0937/M/n=1].
- Branch on the side inside a cook hook as inside an eat hook: the cook dispatch is not side-gated, so a client copy that reaches the cook transition makes the same call in the client's state [#1394/C/C-only, #2066/C/inference].
- Sit in a server-side wrapper of the eat action's completion when the mod needs the item before `Eat` touches it: the wrapper must hold its sentinel outside any table the shared file re-creates, guard on a nil-checked `isServer()` because the mod's `server/` file also runs in the client VM, and call the original unless it means to skip `Eat` entirely [#1190/M/n=1, #1033/M/n=1].
- Hold a wrapper's sentinel in a global of its own: the shared file re-creates its state table by plain assignment on every load, so a sentinel kept inside it is wiped while the old wrapper is still installed and the next install wraps the wrapper [#0943/C/C-only].
- Monkey-patch idempotently and keep the original, testing for your own wrapper before you replace the target: that shape is safe under a Lua reload, unwindable, and it composes when two mods wrap the same function [#1067/C/snapshot].
- Write an `OnEat` correction as a delta on the store the eat has already filled, never as a second intake: the hook fires after every stat and nutrient write, so vanilla's numbers are already in [#0008, #2062/C/inference].
- Put item data in scripts and reach for a Lua field write only when the field is in `ItemStatsPacket` or the value may stay server-only: a script value is identical on both sides for free, while a Lua write to a live item never leaves the server [#1074/M/n=1].
- Scale an eaten item's mod nutrients to the calories `Eat` delivered: the item's `getCalories()` read before the eat times `Eat`'s own fraction, over the table's calories, and fall back to the hunger ratio against the script only when the table's or the item's calories are zero or absent, because fish, cut fish, small-animal cuts and foraged wild food scale their macros and their hunger by independent factors while a partial eat scales calories and `hungChange` together [#3326/C/C-only, #3329/C/arith., #3330/C/C-only, #3331/C/C-only, #3332/C/C-only, #3333/C/C-only, #3340/C/inference].

## How it works

This page owns no mechanism: it reads [the hook dispatch](../platform/lua-platform.md#script-hooks) against [the order of writes](../facts/eating-pipeline.md#eat) and [the cook block](../facts/cooking-and-recipes.md#cook-block) to ask where a correction can sit, and [the options table](#hook-options) sets the seven sites side by side.

<a id="side-choice"></a>
### Which side a hook must sit on

The server owns every store an eat writes, so the side comes first.
The server drives the client's net action into the eat action's completion and on into `Eat` [#0110], and a client write to hunger, thirst, calories or the macros is erased by the next player-stats push ([#0568/M/n=2], [mp-model.md#routes-client-to-server](../platform/mp-model.md#routes-client-to-server)), so a mod runs its intake math on the server, where the eat runs [#1128/M/n=1].

The eat hook runs on both sides, and its client arm is a notification, not a second intake [#2004/C/C-only]; it fires on the eater's own client only, because the eat packet goes through the player-addressed send ([#0130], [#2603/C/C-only], [mp-model.md#sync-globals](../platform/mp-model.md#sync-globals)).
A completion wrapper installed from a `server/` file acts on the server only; it installs on the client too, where it stays silent [#0928/M/n=1].
Two lessons rules fix its install and re-wrap discipline ([#2844/C/inference], [#2845/C/inference], [lessons.md#rules](../platform/lessons.md#rules)).
The completion already carries a corpus mod's sentinel-free save-and-replace on the server, so a wrapper beside it calls the saved original on every path that does not mean to skip the eat [#2562/C/snapshot] [#2566/C/snapshot] [#1067/C/snapshot].

A mod can refuse on the server an eat the client's own gate let through. In the worked example, in Mode 1 this mod's server-side wrap of the eat action's start, which vanilla does not define, refuses an eat of a food whose hunger change is below 0 while the eater's record in memory reads Overfull 4: it marks the action refused, force-completes it and sends the player vanilla's cannot-eat-more text; the action's completion then returns false, the engine's reject, with nothing below it run, and its server stop eats nothing, the one place the mod's eat wrappers do not call the original; below Overfull 4 and on the client the original runs unchanged, and a drink from a fluid container, which is no eat action, is never refused [#3979/C/inference].
Played live at Overfull 4, a Broccoli queued from an empty client queue was refused by the server: the guard's refusal count went from 0 to 1 and nothing landed, the item kept its id 2114768171 and its count of 2, the record's eat count stayed 0, the client's queue was left empty, and 0.20000000298023224 L of water drunk after it landed [#3989/M/n=1].

The cook hook is reached only by the side that runs the cook transition, the server on the measured path [#0925/M/n=1], and the creation hook runs on whichever side instantiates the item, read from the bytecode and never fired [#0926/C/C-only].
No folder decides a side: a mod's `server/` Lua runs in the client's state as well ([#0854/M/n=1], [overview.md#two-lua-states](../platform/overview.md#two-lua-states)), so the side is a nil-checked branch inside the hook, for the reason [the dialect's limits](../platform/lua-platform.md#kahlua-limits) give.

A client arm reads the same post-intake numbers as the server's, because the eat packet's parse has loaded the server's store before the twin fires the hook ([#1034/M/n=1], [#0116], [wire-packets.md#eat-food-packet](../facts/wire-packets.md#eat-food-packet)), so it can drive a display or a prediction.
It cannot change what an eat delivers, because the packet's handlers apply no numbers of their own [#0116], nor push an item field to the server, because every arm of the item-stats send runs server to client [#1150/C/C-only].
The mod's own fields kept there are never overwritten by the push, and they drift from the vanilla numbers the server keeps recomputing [#0129/M/n=1].
A mod that needs the client's input on an intake sends it over the command bus to the server's arm ([#0932], [mp-model.md#command-bus](../platform/mp-model.md#command-bus)).
An eat of a client-spawned food ends in a sync error on the server ([#0124/M/n=1], [mp-model.md#packets](../platform/mp-model.md#packets)), and whatever a creation or cook hook writes into an item field reaches the other side only if the item-stats packet carries that field ([#1036], [wire-packets.md#item-stats-packet](../facts/wire-packets.md#item-stats-packet)).

<a id="seat-in-the-order"></a>
### Which seat sees which values

The eat path writes in one fixed order, which [the eating page](../facts/eating-pipeline.md#eat) owns [#0006]; this is where each seat falls in it.

The completion wrapper, ahead of its call of the original, is the one seat that sees pre-intake values: the store before the eat, and the item before `Eat` reads or changes it ([#1033/M/n=1], [#1129/M/n=1]).
What it writes there is what `Eat` then reads, a reading of the order no session has exercised, and it stops the eat only by not calling the original, which skips the whole eat [#0006, #1129/M/n=1].
It does not yet know the share the eat will take, which `Eat` rescales from the menu's share of the whole item into a share of what is left ([#0014/M/one-fixture], [eating-pipeline.md#modifiers](../facts/eating-pipeline.md#modifiers)); a copy of that rescale, already duplicated twice in Lua, follows the two-fractions rule, a live-read quantity by the share of what is left and a whole-instance quantity by the share of the whole ([#0082], [#2843/C/inference], [eating-pipeline.md#partial](../facts/eating-pipeline.md#partial)).

The eat hook is the post-intake seat: it fires after every stat and nutrient write and before the item is consumed ([#0008], [#0093]), so the item is still the one the eat read [#0008] and a correction is a second write on top of vanilla's [#1130/M/n=1].
It is handed the rescaled share, not the menu fraction [#0093], and it can still reach the leftover: the leftover scaling multiplies a mutated remaining hunger or calories, read off the order of the two calls and never measured [#0094/C/inference].
On the item, the state-modified getter pair gives what the player received and the raw pair what the item still stores ([#0102/M/one-fixture], [eating-pipeline.md#getters](../facts/eating-pipeline.md#getters)); a correction that recomputes from the item's own macros applies the burnt divisor, the game's one nutrition modifier, or overstates a burnt item ([#0019/M/one-fixture], [#0036/M/one-fixture]); and a utensil reaches only the mood and sickness call [#0009].
The hook fires for any character that eats, while the nutrient block is skipped for a non-player and the nutrition object is declared on the player class alone, so a nutrient correction tests for a player first ([#0006], [#0020], [#0897/C/C-only]).
A nutrition write made in the wrapper ahead of the original rides the eat packet, which carries the whole store, while a post-intake write waits for the once-a-second push ([#0113], [#0114], [wire-packets.md#player-stats-packet](../facts/wire-packets.md#player-stats-packet)).
Every post-intake seat sees the stores after their clamps discarded any overshoot, so only the wrapper's pre-intake reading shows what a clamp threw away ([#0021/M/one-fixture], [#0022/M/n=2], [#0023/M/n=2], [nutrition-core.md#clamps](../facts/nutrition-core.md#clamps)).

A wrapper that calls the original and then acts takes a third, later post-intake seat: the stores are written, the eat hook has run and the item is consumed or scaled down and synced, all on the server [#0006, #1032/M/n=1].
A mood add there lands after `Eat`'s own boredom and unhappiness adds [#3655/C/C-only]; the worked example's wrapper only books the eat, and its writer holds a mood floor once a game minute ([#3658/C/inference], [body-effects.md#effects-seats](body-effects.md#effects-seats)).
With both seats in use the server runs the wrapper and then the eat hook, and the client runs the eat hook alone, after the eat packet has replaced its store, reading the post-intake values the server's arm read [#1033/M/n=1, #1034/M/n=1].
So a correction that must change what an eat delivers sits in the wrapper ahead of the original; one that may correct afterwards sits in the eat hook or behind the original, and pays a second write and a push of lag.

The menu offers fractions below a whole item, and the eat hook receives the rescaled share of each ([#0078], [#0093]).
It fires once per portion: four completed quarter eats of one item fired it four times on each side and a whole eat once more, each handed `Eat`'s rescaled fraction of what was left [#0929/M/n=1, #2830/M/n=1].
A finishing eat divides 0 by 0 in the consume step by the jar's reading, so a wrapper's share computed from the raw hunger after the eat reads NaN, not 1 [#2832/M/n=1].

A cancel resolves on the server through the net action's stop and the server-stop step, whose fraction is the net action's progress ([#0111], [mp-model.md#ownership](../platform/mp-model.md#ownership)); the eat hook, which fires inside `Eat`, sits on that route too and is handed a share rescaled like any other [#0111, #0093], so a mod can handle a partial or cancelled eat there [#1132/C/C-only].
Two guards on the server-stop step make a cancelled eat apply nothing at all — no stats, no nutrition, no leftover scaling, no consumption, and no eat-side seat fires — for one named item and for any item whose state-modified hunger change sits at or under the magnitude the guard tests [#0112].
The guard's live reading against the mod is [X33's](open-questions.md#x33).

The wrapper can also change what an eat delivers without writing a stat, by lowering a stored item field `Eat` reads and restoring it after the original returns.
In the worked example this mod lowers a sad food's stored `UnhappyChange` in its server wrapper ahead of vanilla's eat, so vanilla applies the scaled read-time value with its own share and utensil factor, and after the eat restores the field the remainder would have kept and, while the remainder is still in a container, syncs it to the eater's client [#4160/C/inference]; its kernel scales a sad `UnhappyChange` by 0.6 while its HUNGER is over the Hungry threshold, never the happy side [#4158/C/inference].
Played live, a sated eat of 0.2999999937911827 of a butter raised UNHAPPINESS by 6.0, the field times the share, with the scale at 1 [#4143/M/n=1], and a Hungry eat of 0.42857146024906756 of it raised UNHAPPINESS by 3.5999984741210938 against the field times the share, 6.000000443486946, a ratio of 0.5999996889205481 to the sated eat's [#4144/M/n=1].
After each of five eats, sated and Hungry, the eaten item's server field was its field before times the remaining share, and on the three Hungry eats the restore counter read 3 [#4145/M/n=1]; a whole lard eaten Hungry and cancelled through the action queue's clear ate 0.3591438214786211 of it, and the part eaten was scaled [#4146/M/n=1].
With the re-sync the rules require, a Hungry eat of a third of a stale potato's remainder (f 0.333333388522817, alliesthesia scale 0.6) left the server's stored `UnhappyChange` 2.5, its field before 3.75 times the remaining share, read-time 12.5, and the eater's client copy a stored 12.5, the server's read-time value [#4170/M/n=1]; vanilla's own part-eat is [the item-stats packet's](../facts/wire-packets.md#item-stats-packet).

A drink from a fluid container sits outside all of these seats ([eating-pipeline.md#fluid-path](../facts/eating-pipeline.md#fluid-path)).
The drink action calls `DrinkFluid` incrementally from its update and its animation event rather than from a completion step [#0085/C/C-only], through its one call in `updateEat`, which the completion reaches as well, so a wrapper there sees each sip once [#2689/C/C-only].
Measured once on a live server, a wrapper there fired on the server while the client's counters stayed at 0, its install there not witnessed, and a second save-and-call-original wrapper stacked on the same method counted every call the first counted and landed the drink in its own store ([#2825/M/n=1], [#2826/M/n=1]).
In the worked example played live on the release, a world-water drink reached the mod's intake: `water.take` from a source 3.6 tiles from admin raised the intake's world-sip count from 0 to 14 and the stomach's liquid lane from 0 to 892.17, and at the next write THIRST read 0.08299 against 0.44517 before, the record's thirst target 0.08386 against 0.44391, while the meal pool M read 8.846 against 11.894 [#3777/M/n=1] [#2942/M/n=1].
`DrinkFluid`'s body holds no Lua call, so a wrapper of one of the two drink actions is the only Lua seat on either route [#2687/C/C-only] [#0084/C/C-only], and no live version folder in the corpus names `updateEat`, so a drink wrapper there has no other wrap to chain onto, by one sweep of a corpus that drifts [#2567/C/snapshot].
A drink's calories reach a client only on the once-a-second push [#0649].
A food item with a thirst change and the drink menu option goes through `Eat` like solid food, and every seat above applies to it [#0083/M/one-fixture].
The sandbox nutrition switch gates the update tick and never the intake, so no seat moves when a server turns vanilla nutrition off ([#0067], [eating-pipeline.md#sandbox](../facts/eating-pipeline.md#sandbox)).

<a id="cook-seat"></a>
### Where a cooking-side hook sits

The cook hook sits inside the item's own update, on the transition to cooked, rather than inside an action a player queues ([#0257], [cooking-and-recipes.md#cook-block](../facts/cooking-and-recipes.md#cook-block)).
It fires after the block has set the cooked flag and cleaned the item's mood and age fields, and before the microwave penalty ([#0257], [#0045], [#0268]), so mood fields a hook writes on a bad-in-microwave item cooked in one are then penalised [#0269].
The transition is entered only while the item is neither cooked nor burnt, so the hook does not fire again on an item it cooked and a multiplying rewrite does not compound on that side [#0257].

The transition moves no stored nutrition: cooking and burning leave calories and raw hunger untouched and move only the read-time hunger ladder ([#0277/M/n=1], [cooking-and-recipes.md#type-change](../facts/cooking-and-recipes.md#type-change)), and cooking as such moves no calories anywhere in the recipe data [#0742/C/snapshot].
A mod that wants cooking to change what an item delivers rewrites the instance from the cook hook or names a different item in the script.
The cook hook can rewrite a crafted instance, its registration and firing read rather than driven end to end [#1154/M/n=1]; one corpus mod's server-side cook hook does so, printing in the server console ([#1208/M/n=1], [the teardown](../facts/other-mods/longtermpreservation.md#architecture)).
The client then receives the calories, proteins, lipids and raw hunger that hook scales intact, never the age-window bounds or the cookable flag ([#1105/M/n=1], [#1037/M/n=1], [wire-packets.md#desyncs](../facts/wire-packets.md#desyncs)); the carbohydrates ride the packet by a read of its fields, since the measured item carries none on either side of the rewrite [#1105/M/n=1].
Anything else a cook hook writes has to be a field the packet carries or a value left on the server [#1074/M/n=1].

A rotten item carrying a `ReplaceOnCooked` link is not swapped and takes the ordinary path through the cooked flag and the hook [#0266].
A swap delivers the replacement's own script values, and none of vanilla's three `ReplaceOnCooked` links moves a macro [#0752/C/arith.]; the replacement's script loads on both sides without a packet ([#1058/M/n=2], [loader-and-scripts.md#per-side-load](../platform/loader-and-scripts.md#per-side-load)).
The transition and every swap are driven by server-owned state ([#0758], [mp-model.md#ownership](../platform/mp-model.md#ownership)), and the measured transition ran on the server, the hook's prints in the server console and the client's empty [#1417/M/n=1].
No session has fired a dotted cook-hook name, so that half of the dispatch is a bytecode reading [#3502/C/C-only].

The cook hook changes what an item is after it cooks, never how it cooks: per-item cook times are the script's [#1156/M/n=1], and spice behaviour is the `Spice` script bool, which routes an ingredient down the evolved summation's spice branch, ending in `useSpice`, which lowers the dish's unhappiness and boredom by twice the recipe's `:N` and moves the spice's macros into the dish at the skill bonus times its share [#4127/C/C-only].

No craft seat has been fired: nothing on the bus executes a craft, so a recipe's creation and test hooks and the item-block creation hook stay bytecode readings ([#1248/C/C-only], [harness.md#walls](../platform/harness.md#walls)).
A set of output-less recipes mutate an input through a creation hook instead of yielding an item, and what those hooks do to nutrition is unread ([#0686/C/snapshot], [#0784/C/snapshot/open]).
A craft recipe's own creation hook is handed the recipe data and the character only after the outputs exist, inside a stop that returns at once on a client, and a client cannot create craft outputs for real, so by the code it is a server seat ([#2665/C/C-only], [#2664/C/C-only], [#2667/C/C-only], [cooking-and-recipes.md#craft-split](../facts/cooking-and-recipes.md#craft-split)).
It reads the consumed instances and writes onto the created ones through the recipe data, the one place a mod value crosses a craft, because no vanilla craft arm copies an input's modData to an output ([#2666/C/C-only], [#2660/C/C-only]).
On a dedicated server the hand-craft action's recipe step runs inside the action's completion, gated on `isServer()`, and a client in a session never runs it [#3564/C/C-only].
A server-side wrapper of that step reads the created outputs after the original returns: the output list is cleared and refilled when a craft creates its outputs, and the step that destroys the used inputs after the `OnCreate` neither clears nor marks it, so it answers the objects the action placed in the inventory or on the floor, unless the recipe's `OnCreate` cleared the list, as the one Java `OnCreate` that unpacks a box of jars does and any Lua `OnCreate` can [#3565/C/C-only].
Such a wrapper names the recipe by `CraftRecipe.getName()` and writes the four macros with `Food`'s plain setters, which store their argument and nothing else [#3566/C/C-only]; those macros and the raw hunger travel in the item-stats packet, which the server-side global `sendItemStats(item)` sends to the owning player or, for a floor item, to nearby clients [#3567/C/C-only, #1105/M/n=1].

The evolved summation calls no Lua and fires no event, and the timed action's call of the recipe's add-item method is the only bridge into it ([#0325], [cooking-and-recipes.md#evolved](../facts/cooking-and-recipes.md#evolved)); a server-side wrapper of the add-item action's completion holds the ingredient instance, the base and the chef before its call of the original and the finished dish after it [#2657/C/C-only, #2658/C/C-only].
The dish lists its ingredients' full types, one entry per add and none for a spice, with no amount or hunger share, so an eat-time reader rebuilds only a nominal share per type ([#2650/C/C-only], [#2652/C/C-only], [#2653/C/C-only]); it starts from its result type's default modData, so an ingredient's mod value reaches it only through that wrapper [#2656/C/C-only].
The Cooking level that scales the summation is the server's, whatever a client shows [#0759/M/n=1]; the measured summation arithmetic is a client-side reading, and what a server stores after a real add-item action is unmeasured [#0360/M/one-side].
Its mood is read on the server: vanilla's add-item action, queued from the chef's client, reached a server wrapper of its completion at every add, and at Cooking 3 the dish's stored `UnhappyChange` was the summation's own arithmetic, add by add ([#4131/M/n=1], [#4132/M/n=1]).
A mod that drives the evolved path queues the vanilla add-item action and inherits its guarantees, as the one corpus mod that automates it does ([#1354], [autocook.md#techniques](../facts/other-mods/autocook.md#techniques)); that mod ranks ingredients on the vanilla macros and weight flags, so new mod nutrients are invisible to its diets ([#1377/C/snapshot], [autocook.md#compat](../facts/other-mods/autocook.md#compat)).

A mod can make an evolved dish's mood depend on its chef's Cooking level from the add-item wrapper, the one seat holding the chef and, after its call of the original, the dish: in the worked example this mod scales a dish's stored relief by the chef's level after each add, stamps the scale in the dish's modData and restores the vanilla value before the next add, so vanilla's arithmetic runs on its own value and a dish of many adds is scaled once, by its last add's chef [#4159/C/inference].
Its curve is 0.8 at Cooking 0, 1 at Cooking 3 and 1.5 at Cooking 10, and never touches a dish's sad side [#4158/C/inference]; it reaches an evolved dish only, and a fixed recipe's cooked result, a cooked plain item and a spawned dish keep vanilla's mood [#4159/C/inference].
Played live, Stir fries made at Cooking 0 and at Cooking 10 each read the Cooking-3 dish's stored relief at the same add times one scale, never compounded across five adds of which two were spices [#4133/M/n=1], and the chef's client copy carried each dish's value and its stamp [#4134/M/n=1].
A food rename from the chef's client, which syncs the dish's fields back to the server, and a relog each left the stamp in place, so the next add read the Cooking-3 dish's value times 1.5 ([#4135/M/n=1], [#4136/M/n=1]), and two dishes made at Cooking 10 and eaten whole moved UNHAPPINESS by their stored values, with no further scaling [#4150/M/n=1].

## Options

<a id="hook-options"></a>
### Hook sites

| option | what it costs | which wall it hits | tags |
|---|---|---|---|
| a `server/` wrapper of `ISEatFoodAction.complete` — server only, ahead of `Eat`: sees the store and the item before any intake, can change what `Eat` reads, or skip the eat whole | a sentinel outside the shared table, a nil-checked side guard, the original called every time; its own copy of the fraction rescale; never sees a cancel | cannot stop part of an eat; one eat at full fraction measured | [#1129/M/n=1, #1033/M/n=1] |
| `OnEat` — both sides, the client arm a notification; after every stat and nutrient write and before consumption, so it corrects the store after the fact and can change the leftover, never the intake | a second write on vanilla's, a side branch, a correction one push late; on both the completed and the cancelled route | cannot fire once in multiplayer; return value ignored; fires once per portion | [#1130/M/n=1, #1131/M/n=1, #2830/M/n=1] |
| `OnCooked` — the side that runs the cook transition, the server on the measured path; after the cooked flag, so it can rewrite the cooked instance's nutrition | only packet fields reach the client; a side branch, since the dispatch is not side-gated; a swapped item never reaches it | never driven end to end; heat gate, tick and perk scaling are Java | [#1154/M/n=1, #1155/M/n=1] |
| `OnCreate` — once, at instantiation, on whichever side instantiates, so it can seed an item before anything reads it | a bare global like the eat hook's; a seeded item field crosses only as the item packet carries it | never fired; nothing on the bus executes a craft | [#0926/C/C-only, #0967/C/C-only/open] |
| a `server/` wrapper of `ISDrinkFluidAction:updateEat` — the drink action's one `DrinkFluid` call, reached from the update, the animation event and the completion; litres and mix sampled before the call and litres after see each sip once | a sentinel and the original every time; the mix sampled before, since the removal returns an aggregate with no per-fluid breakdown; a second wrap of `ISTakeWaterAction`, whose world-source drink uses a temporary container | server only, misses a direct `DrinkFluid` call, one session measured; `DrinkFluid` calls no Lua and touches no modData | [#2689/C/C-only, #0085/C/C-only, #2690/C/C-only, #2688/C/C-only, #2687/C/C-only, #1133/M/n=1, #2827/M/n=1] |

## Walls and bounds
<a id="walls"></a>

- The drink path's one intake seat is a server-side wrapper of the drink action, measured in one session: there is no eat-hook twin, the wrapper fires on the server while the client's counters stayed at 0, and it misses a direct `DrinkFluid` call ([#1133/M/n=1], [#1279/M/n=1], [#2827/M/n=1]).
- No client arm fires for another player's eat: the eat packet reaches the eater's own connection only [#2603/C/C-only].
- No vanilla hook runs ahead of the eat's writes: the eat hook, the only hook on the intake path, fires after them, and the stats, nutrients, pain, cold, sickness, mood and packet sends land with no hook between, so pre-intake work needs the completion wrapper, a workaround rather than a hook ([#0006], [#0130], [#1129/M/n=1]).
- No seat vetoes part of an eat: the eat hook's return value is ignored, and the wrapper stops an eat only by skipping the original whole ([#0093], [#1129/M/n=1]).
- The named-hook roster has no eat, drink, consume, digest or nutrition hook; the stat tick's hook, the one near intake that replaces vanilla work, is all or nothing and no intake seat, and the auto-drink hook fires on the thirst-relief path, not on intake ([#1133/M/n=1], [#2238/C/C-only], [#0482/C/C-only], [lua-platform.md#hooks](../platform/lua-platform.md#hooks)).
- No hook reaches the cook block's gates and timers or the evolved summation's perk scaling, all of which are Java [#1155/M/n=1].
- No hook runs inside the evolved summation and no vanilla craft arm carries modData from an input to an output, so a dish or a craft output carries a mod value only where the mod writes it ([#2657/C/C-only], [#2656/C/C-only], [#2660/C/C-only], [cooking-and-recipes.md#walls](../facts/cooking-and-recipes.md#walls)).
- The cooking pipeline has never been driven end to end: the cook hook's registration and firing are read, the measured side is one mod's single transition per session, and nothing on the bus executes a craft ([#1154/M/n=1], [#0925/M/n=1], [#1248/C/C-only]).
- The eat-hook and wrapper readings are single dedicated-server sessions: one whole eat in one, four quarter eats and four whole eats of one fixture in another ([#1031/M/n=1], [#1033/M/n=1], [#2830/M/n=1]).
- Two save-and-replace wrappers of the eat completion can form a call cycle that blocks every eat: a wrapper that re-installed itself at a later boot event over a later-loading wrapper, while its first closure called its saved original through a global the re-install overwrote, recursed on every completed eat until it overflowed the stack, and no eat ran in eight of eight [#2835/M/n=1].
- A field lowered before vanilla's part-eat stays lowered on the eater's client without a re-sync: on the build before it, after a Hungry eat of a third of a stale potato (f 0.333333388522817), the client read a stored `UnhappyChange` of 8.833333015441895 while the server read 2.5, read-time 12.5 [#4148/M/n=1], and with it the client read 12.5 [#4170/M/n=1].
- A non-finite number an intake wrapper lands is not stopped by the stat clamp: a finishing eat's NaN share, carried into a hunger stat written from the wrapper's store, read as non-finite on both sides [#2833/M/n=1].
- Single player is never claimed: there a cancelled eat action calls its own server-stop step, and the two arms are one process ([#0103], [mp-model.md#ownership](../platform/mp-model.md#ownership)).

Not covered: the thirst-relief path beyond its named hook, the context-menu and crafting timed actions that lead into cooking, hooks a third-party framework layers over these sites, animal feeding beyond the eat call's player guard, and single player — none was read for a hook seat.

## Open
<a id="open"></a>

- Whether a dotted cook-hook name fires, on which side, and whether the cooking pipeline can be driven end to end — settled by a cook-transition session with a dotted target and a harness craft command that reaches a crafted instance; it decides whether cook-side code may live in a table and whether any cooking-side seat is more than a reading; -> X31 ([#1297/C/open], [open-questions.md#x31](open-questions.md#x31)).
- Whether the item-block creation hook fires as the bytecode reads, and what it can seed at instantiation — settled by the same craft session with the hook registered; it decides whether per-item nutrient values are seeded at instantiation or read from the script on demand; -> X31 ([#0967/C/C-only/open], [lua-platform.md#open](../platform/lua-platform.md#open), [open-questions.md#x31](open-questions.md#x31)).
- What the creation hooks of the output-less recipes do to nutrition — settled by executing one on the game's own craft path; it decides whether those recipes need a nutrition delta of their own; -> X31 ([#0784/C/snapshot/open], [cooking-and-recipes.md#open](../facts/cooking-and-recipes.md#open), [open-questions.md#x31](open-questions.md#x31)).
- Whether a declared nutrient vector on an instance whose calories and hunger were scaled apart can be anchored on the type's script calories — those calories are read only off a fresh instance made through `instanceItem` [#2679/C/C-only], which runs the type's `OnCreate` on the server [#3327/C/C-only], and a fish's `OnCreate` scales the fresh instance's macros by a randomly drawn weight [#3328/C/C-only]; settled by a read of a type's script calories that runs no `OnCreate`; it decides whether a declared vector follows the calories `Eat` delivered or keeps the hunger ratio; no `X` id ([#3595/C/open], [open-questions.md#index](open-questions.md#index)).
- Decision: whether the intake correction sits in the completion wrapper, before `Eat` writes, or in the eat hook, after it — only the wrapper sees pre-intake values, while the eat hook's store already holds the eat ([#1033/M/n=1], [#0008]).
- Decision: whether the correction must also cover a cancelled eat — a cancel reaches `Eat` through the server-stop step and never through the completion step [#0111].
- Decision: whether a cooked item's nutrition comes from a cook hook on the instance or from a replacement item's script — the swap returns before the hook runs, and a hook's item-field writes reach the client only where the item packet carries them ([#0266], [#1036]).
- Decision: whether the intake correction also wraps the world-source drink action — a drink-action wrapper never sees a drink from a world water source [#2690/C/C-only].
