## Cross-group duplicates

The rule applied (brief Step 2, amendments para 2, controller ruling): fold only where two
rows state the **same fact** and one pointer set **equals or nests** in the other, comparing a
`run:` pointer at run-and-file granularity (so a keyless row and the keyed one are the same
pointer) and a `jar:` pointer at method granularity (so a dash or line-format variant of one
site is the same pointer). Nothing is ever deleted: the duplicate keeps its id and its cells,
takes `status superseded` with `successor` the kept row, and its `source` is appended to the
kept row's. A wall-map `verdict` row is never folded into its `mechanism` row, a parent row
never into its child (R26), and a pair whose claims differ in scope is kept and recorded.

A bound or a pointer that only the superseded row carries is **not lost** - the row is still
in the register, and a reader following `successor` reaches it - but the live row is the one a
page tags, so every such case is named below.

### How the pairs were found

Three passes over the merged register, cross-block only
(`merge-duplicates.py`, in the harvest workspace, kept locally outside the tree): identical normalised claim
text (**0 groups**, as the controller's dry-merge scan also found); identical pointer set; and
nesting pointer sets, with a fourth pass comparing evidence roots (run + file, jar method) so a
keyless row meets the keyed one. Candidates were ranked by claim-word overlap and every pair
above 0.35 was read by hand; the controller's `drymerge-duplicates.tsv` (125 shared-pointer-set
groups) was the floor, and its eight large groups are dataset `data:` / `web:` pointers shared
by `count` rows and one jar range shared by seven rows - legitimate grain, not duplicates.
