# Workshop neighbours and the compatibility stance — a desk read

Research note for the nutrition mod design (spec `docs/superpowers/specs/2026-09-27-nutrition-mod-design.md`), fetched 2026-09-27.
Scope: public Steam Workshop pages only. **None of these mods is installed here, so no code was read.** Every reading below is of an item page or of a Workshop browse listing, and each entry says which; **no change-note page and no discussion thread was reachable on this read** (see `## Method` — Steam rate-limited the item-detail path after four pages). Where a sentence is an inference rather than something a page says, it is marked *(inferred)*.

## Summary for the design

The Workshop neighbourhood this mod will ship into has exactly one real rival and a great many small ones, and the design should treat those two facts differently. The rival is `3690404044` Nutrition Makes Sense, at 7 729 subscribers and updated the day before this read, which by its own description already owns hunger, fullness, energy, body weight, a nutrition window, a food tooltip, a malnourished moodle and the macro values of roughly six hundred vanilla foods — the same surfaces the spec claims, for the same reasons. No compatibility rule reconciles two complete models writing the same hunger stat, so the honest stance is to name it in the release notes as the mod this one replaces, and the honest first task before release is to read its code to learn whether it registers `Hook.CalculateStats`. Everything else on the nutrition shelf is smaller than expected: Nutrition Tweaker Enhanced has 1 514 subscribers but only scales vanilla's macro drift, which the takeover deletes, so it becomes silently inert rather than conflicting; Reasonable Nutrition (205) and Realistic Nutrition (55) are pure item passes whose only collision with ours is per-key merge order, a load-order note rather than code. Ruling 5's stated wall — the hook is global and all-or-nothing — is the one place where page-level evidence cannot reach a verdict, and the two published stat libraries found here, `2997722072` StatsAPI and `3415375593` Stat Tweaks Lib, are the most plausible rival claimants precisely because a generic stat-tweaking library has the same motive the spec has; whether either claims the hook decides whether overlay mode is an escape hatch or the mode a public release ships in.

The small mods matter in aggregate and they cluster by surface, which makes them tractable. Nine endurance and stamina tweaks, five hunger and thirst tweaks, five fatigue writers and three body-weight mods all write stats the model owns and will be silently overwritten within one tick; that is not a bug to fix but a sentence to write, and the sentence must be in the release notes, because a silent no-op reads as a broken mod to a user. Eleven eat-and-drink mods sit directly on § 4.2's wrappers, and the family splits usefully: wrappers coexist, but mods that replace the action class or change the portion size defeat the intake read, which argues for adding a missed-intake reconciliation on the slow clock so an uncounted eat becomes a one-minute lag instead of a lost meal. At least fifteen status viewers and around twenty moodle mods crowd § 4.7; the finding that changes a design default is that § 4.9's existing "a status viewer with hard-coded bands miscalibrates" rule cannot name one mod because there are fifteen, and the cheap general fix is a sandbox-selectable legacy macro mirror that keeps the vanilla macro slots populated with the model's own equivalents, turning fifteen broken third-party UIs into fifteen working ones for a few lines on the slow clock. Two smaller design changes fall out of the same reading: the moodle fallback column should be independently positioned rather than anchored to a vanilla stack that twenty mods move, and `3694097672` Tooltiplib should be read before the tooltip wrap is written, because a published tooltip framework and a mod that exists only to reconcile tooltip heights (`3787441060`) together say the stacking problem is real and already has a seam.

Three findings are worth more than their size. First, compatibility work is cheapest when expressed as multipliers rather than absolutes: the medical family and the carry-capacity family both resolve as last-write-wins on shared fields, and a read-modify-write discipline makes the mod compose with about forty mods at no cost. Second, the food-content long tail — Vanilla Foods Expanded and a dozen cuisine mods — is not a conflict at all, since no installed mod in the library's 230-folder corpus overrides a vanilla food; but a third party already ships a VFE-to-NMS compatibility patch, so users will ask for ours, and the answer that scales is to infer a nutrient vector for unmapped third-party foods from their own macro keys and food type, plus a documented modData key any author can set. That one decision converts the largest family in this note from a patch queue into a default, and it is the highest-leverage compatibility choice available. Third, three of the most instructive collisions are already readable on this machine and need no subscription: `SomewhatTraitsCore`'s `SWAdaptiveMetabolism`, the corpus's only player macro write, fights body composition every tick; `SkillRecoveryJournal` reads `getProteins()` in `shared/` to gate fitness XP, so re-basing the macro scale silently moves its thresholds; and `simpleStatus` is a ready-made test of the re-based-scale miscalibration. Those are three free live experiments and they should be run before any of the five shortlisted subscriptions.

One page earned its own paragraph. `3736275816` ApocalipseBR - Nutrition Sync Fix (738 subscribers) states the vanilla multiplayer failure in the author’s own words — the client’s local calorie counter never decays by design, and every eat ships that inflated client value to the server, overwriting the server’s correctly-decayed state, so players only ever gain weight — and fixes it by polling the server for authoritative macros every 120 s. That is a third party arriving independently at the client-mirror-versus-server-store reading the library already records, which makes it worth a register row. It also carries a warning aimed squarely at ruling 5: **disabling the vanilla `Nutrition` sandbox option stops calorie decay while still permitting weight gain.** Under full takeover that is harmless only because the mod writes the weight slot itself every slow tick, so the test plan needs a named negative case — `Nutrition` off, the mod’s weight write disabled, weight must not drift upward — and the stance on the mod itself is coexists-but-redundant, with its sync module disabled.

Two cautions on how far this note reaches. Steam rate-limited the item-detail path after four pages, so the six named nutrition mods are only four-sixths read and every family below them rests on a title and a search term — no change notes and no discussion threads were read at all, and the instruction to search discussions for `CalculateStats` could not be carried out because the web-search budget was already spent when the task began. The families are therefore reliable as a map of *where* the neighbours are and provisional as a claim about *what any one of them does*. And the surface moves fast: four mods carrying ids newer than anything in the library's 2026-09-10 sweep turned up in today's `nutrition` listing alone, one of them a direct rival on the hunger model, `3809133438` Realistic Hunger (Prototype). A compatibility stance written once will be stale by release, so the release notes should carry the stance as a short set of mechanism rules — who owns which stat, what happens to a mod that writes it, which surfaces are shared — rather than as a list of mod names that has to be maintained.

## Surface shorthand

The nutrition mod's surfaces, from spec §§ 4.1–4.9, abbreviated in the tables below:

| key | surface |
|---|---|
| **HOOK** | `Hook.CalculateStats` — the takeover handler, global and all-or-nothing (§ 4.1, ruling 5) |
| **STATS** | writes to hunger, thirst, endurance, fatigue (the vanilla stat slots the model owns, ruling 2) |
| **NUTRI** | the vanilla nutrition object's macros (calories, carbs, proteins, lipids) or the body-weight slot |
| **STR** | the Strength perk level or its XP, and the lean-mass ceiling that clamps it (ruling 6) |
| **TRAIT** | runtime trait add/remove — night vision, short-sighted, the band traits (§ 4.5) |
| **EAT** | `ISEatFoodAction.complete` / `serverStop`, `ISDrinkFluidAction:updateEat` wrappers (§ 4.2) |
| **UI** | the inventory tooltip wrap, the character-info tab, the panel, moodles (§ 4.7) |
| **ITEMS** | `module Base` partial item blocks re-basing `Calories`/`Carbohydrates`/`Proteins`/`Lipids` (§ 4.6) |
| **SBOX** | sandbox options, and the vanilla `Nutrition` option the takeover turns off |
| **NET** | the engine's player-stats push and the trait packet, and the mod's own command bus (§ 4.8) |

### 3736275816 — ApocalipseBR - Nutrition Sync Fix

**The most valuable single page in this note.** Its page was fetched late in the session, after the rate limit briefly lifted.

- **Author:** Ricardão · **Posted** 2026-05-31 07:55 · **Last updated** 2026-05-31 11:18 (same day; two change notes exist, text not fetched) · **File size** 453.434 KB · **Requires Build 42.18+** · not installed here
- **Stats shown:** 738 subscribers · 5 favorites · 340 unique visitors · **Tags:** Build 42
- **What it says the bug is (quoted):** "the server is the authority for nutrition and weight. The client's local calorie counter never decays (by design). Every time you eat, the game sends your client's inflated, non-decaying calories to the server — overwriting the server's correctly-decayed state." The symptom is players who **perpetually gain weight** in multiplayer.
- **What it says the fix is:** it syncs the server's authoritative nutrition data down to clients at a configurable interval (default 120 s, range 30–600 s), with an immediate sync on join, keeping weight, calories and macros accurate. Mechanism, in its own words: "Client requests nutrition values; server responds with authoritative data applied locally", operating "through custom commands without interfering with nutrition or food mods." It explicitly does **not** address value corruption or the sandbox nutrition behaviour itself.
- **Sandbox options:** enable/disable the sync module; sync interval (30–600 s); debug logging.
- **The warning that matters most to this design (author statement, verbatim in substance):** **"Do not disable nutrition in sandbox settings, as this stops calorie decay while permitting weight gain."**
- **Surfaces:** **NET** (its own client-request / server-reply command pair — the same shape as § 4.8's bus, in the opposite direction), **NUTRI** (it writes calories, macros and weight on the client), **SBOX**.
- **Evidence quality:** description, author statement, stated sandbox ranges. Strong for a page read. Not code.

**Three consequences for the spec, and the third is a live risk:**

1. **It independently corroborates the library's ownership model and names the exact mechanism.** A client-side calorie store that never decays, plus an eat that ships the client's value up to the server, is precisely the client-mirror-versus-server-store failure the library records ([#1634/C/inference], `facts/wire-packets#staircase`). This is a third party arriving at the same reading from symptoms. It is worth a register row on its own.
2. **It sharpens § 4.2.** If the vanilla eat pushes the *client's* calorie value to the server, then the spec's server-side `ISEatFoodAction.complete` wrapper is reading an item whose macro state may already have been perturbed by a client-authored value in the same action. The wrapper reads *raw hunger on the item* rather than player calories, which is the right choice and is now independently justified — but the mod must also be sure its own store is never seeded from a client-sent macro value.
3. **It contradicts nothing in the spec but it does flag ruling 5's sandbox move.** Ruling 5 turns the vanilla `Nutrition` sandbox option **off**; this author warns that doing exactly that "stops calorie decay while permitting weight gain." Under full takeover that is harmless *if* the mod owns the weight slot and writes it every slow tick — which § 4.1 says it does — but it is harmless only because of that, and the failure if the weight write is ever skipped or gated is silent, one-directional weight gain. **This belongs in the test plan as a named negative case: with `Nutrition` off and the mod's weight write disabled, weight must not drift upward.** It is also a cheap harness experiment and it is a claim a third party has already published, so it can be graded rather than guessed.

- **Stance:** **coexists as designed, and becomes redundant — say so.** Under takeover the mod is the authority and pushes its own mirror on change and at most once a minute (§ 4.8), which is strictly better than this mod's 120 s poll, and the client store the mod exposes is a read-only mirror, so the desync this fixes cannot arise. Two mods both pushing authoritative macro values to a client will fight, at a period of 120 s against 60 s, so the release note should say: **not needed with this mod, and disable its sync module if both are enabled.** Still worth **subscribing and reading once**, not for compatibility but because it is the only published implementation of the server-authoritative nutrition push and its 30–600 s interval range is a free data point on what cadence servers tolerate.

## The neighbourhood, by surface

Beyond the six, the surfaces in § 4 are each crowded by a *family* of small single-purpose mods rather than by one rival. The families below were enumerated from the Workshop's own all-time-popular browse listings on 2026-09-27 (one listing per term; the exact URLs are in `## Sources`). **For a family entry the evidence is the title and the search term that returned it, nothing more** — no description was read — and the stance is therefore a stance on the family, to be checked against any one member before it is quoted at a user.

### The endurance and stamina family — HOOK, STATS

Term `strength endurance stamina`, all-time popular, 2026-09-27. Nine of the thirty results modify endurance directly: `3753252201` Customize_Endurance (CreamPie), `3798260771` Faster Endurance Recovery (+ Justice +), `3664677082` Less Melee Endurance Consumption (MilitarZ2112), `3414599789` [B42.20]Smooth Endurance (030helios), `3387065293` [b42]MoreEndurance, `3127023259` No more stamina B41/B42.17+ (Cowk), `3717515582` Energy Drinks Replenish Endurance (Wlfryt), `3701429858` Infinite Endurance Trait - Mugen (David Hogins), `3790843183` Skilled Swings (Build 42 Stamina Fix) (Teratehs).

This is the **sharpest structural risk in the whole note**, and it is one the spec already half-names. The fast clock reproduces vanilla's endurance updater and writes endurance from the mod's own stored value every tick, "never read[ing] the stat back" (§ 4.1). Any mod in this family that adjusts endurance by reading the stat and writing it back will have its write silently discarded on the next tick; any mod that registers `Hook.CalculateStats` collides with the takeover outright. Nine mods in one listing means the odds that a public server runs at least one are high.

**Stance for the family: detect-and-fall-back is not available** (the hook is all-or-nothing), so: **needs a compat rule in the mod** — a release-note rule reading "endurance and stamina tweaks have no effect in takeover mode; use overlay mode if you need them" — plus **subscribe-and-read-the-code** for one representative, to learn *how* a typical small endurance tweak reaches the stat on this build. That single read tells us whether the family is a silent-no-op problem (survivable) or a hook-contention problem (fatal without overlay).

### The eat-and-drink-action family — EAT

Term `auto eat drink`, all-time popular, 2026-09-27. Eleven of thirty results wrap, replace or suppress the eat and drink actions: `3795435563` [B42] Auto-Eat [SP/MP] (spels47), `3792887660` [B42] Auto-Drink Expanded [SP/MP] and `3737205872` [B42] Auto-Drink Revert [SP/MP] (both ObnoxiouslyNoxious), `3726845507` Slow Eat & Drink [B42] (PhysiksTV), `3808101523` Batch Eat / Eat All (TheFlaxCompany), `3793387564` Sequential Eat (- Nexus -), `3456212729` Eat Smart (Afyrmo), `3723250181` Eating Hotkey (BitsOBacon), `3803043894` AutoDrinkNoMore (Ecn), `3598196432` Disable Auto Drink [B42.15-42.20][MP], `3737061821` Auto Drink All (Mickey Knox).

The spec's § 4.2 wrappers are the idempotent save-and-call-the-original kind and hold their sentinel in a global of their own, which is the shape that survives another wrapper on the same method. The real exposure is different: the intake read is **the drop in raw hunger over the item's base hunger**, so a mod that changes *how much* of an item one action consumes (Slow Eat, Batch Eat, Sequential Eat) changes the share the wrapper computes, and a mod that **replaces** `ISEatFoodAction` with a subclass or a new action class rather than wrapping it bypasses the wrapper entirely and the eat is never counted.

**Stance for the family: coexists as designed for the wrappers, needs a compat rule for the replacers.** Concretely: measure the share eaten from the item rather than from the action's own parameters (§ 4.2 already does), and carry a **missed-intake reconciliation** — if an item's raw hunger changed without a wrapper firing, attribute the delta on the next slow tick. That converts the whole family from a correctness bug into a one-minute lag. Name `3795435563` Auto-Eat and `3792887660` Auto-Drink Expanded in the release notes as the two to test against, both being explicitly `[SP/MP]`.

### The fatigue-and-sleep family — STATS, NET

Term `sleep fatigue`, all-time popular, 2026-09-27. Two are unusual and matter more than the rest: `3778798387` Share Fatigue (Clarkeeroo) and `3790232339` Shared Fatigue Sync [B42.20] (Jl4cTuk) — mods that **write fatigue across players on a multiplayer server**, i.e. they write the exact stat the fast clock owns, on the server, for a player other than the one acting. Also: `3750296207` Drink Fatigue Reduction (GIBKI RASISTA), `3799930734` Apples Reduce Fatigue (Anomaly-Friend), `3787954371` Fatigue Damage Rebalance (Matt101), `3750106953` Fatigue Visualizer (CrispyTyler), `3781533687` True Sleep - Better Multiplayer Sleep (yoona), `3790219243` Multiplayer Sleeping (Monstrplayr), `3419944297` Wolf's No Sleep, `3386833361` No sleep for B42, `3774966407` Sleep & Need [Not Finished!] (Destroxin), `3682030831` More Traits Alcoholic Fatigue Fix (kokickss).

The spec's fatigue is not a stat the mod nudges but an integrated two-process model whose output is written every tick (§ 4.5). Every mod in this family that adds or subtracts fatigue will be overwritten within one tick.

**Stance: incompatible-and-say-so for the fatigue writers, coexists for the readers.** `3750106953` Fatigue Visualizer reads and is fine. `3778798387` / `3790232339` / `3750296207` / `3799930734` / `3787954371` write and are not. The release note needs one line: "fatigue is computed by this mod; mods that add or remove fatigue are overwritten on the next server tick." Sleep-*location* and sleep-*permission* mods (`3781533687`, `3790219243`, `3768136303` MultiSleep, `3752103087` Sleep Offline) do not write the stat and coexist — but the bed-quality input the spec's sleep model scales recovery by is read from the bed, so a mod that adds new sleeping surfaces feeds the model an unmapped bed type. That is a **detect-and-fall-back** case with a trivial fallback: an unknown bed gets the default quality.

### The status-viewer family — UI, and the re-based-scale rule

2. **Readers of the four macros** (Minimal Display Bars + Nutritions, Nutrition Helper UI, Dietary Stats, Nutrition Panel for PZ Pulse, and `simpleStatus`, which the library has read: twelve client-side reads of the macros, the body weight and the three weight-trend predicates, each rounded to one decimal [#1582]). That is a small addition to the slow clock and it converts fifteen broken UIs into fifteen working ones. `simpleStatus` is the one to test against because its code is already read here.

### The trait family — TRAIT, NET

Term `traits`, all-time popular, 2026-09-27, plus the occupations listing. The large ones: **`2914075159` Evolving Traits World (ETW) + More Traits continuation (MusicManiac)** — the biggest trait system on B42 and the one that *adds and removes traits at runtime*, precisely what § 4.5's night-vision and short-sighted toggles do; **`2840805724` SOTO (Simple Overhaul: Traits and Occupations) (hea)**, tagged `[B41/B42SP]` — single-player on B42, with a third party shipping `3763874285` [FIX MP] SOTO 42.20 (Logosh) to make it work on a server; **`3799050151` More Traits Definitive Edition**, `3786253696` Traits As Skills - More Traits and `3784847437` Traits As Skills (all GersonRess); **`3786511330` Dynamic Traits (Wwin12)** — a B42 port of Dynamic Traits, with `3797870358` Dynamic Traits - Wound Infections Nerf (Notixz) as a third-party patch to it; **`3498347699` Somewhat Traits (somewhatfrog)**, installed and read here, whose `SWAdaptiveMetabolism` trait is **the installed corpus's only player macro write** — an `OnTick` server handler adding or subtracting calories to hold body weight in 77–83 kg [#1588]; `3622328997` Adaptive Traits (Mich), `3434453874` Howie's Traits, `3695544498` Occupation Locked Traits Framework [42.15+] (Howie_Dewyn), `3777663603` Even More Traits, `3423601261` [B42] Mastered Traits, `3628752758` B42 Custom Traits, `3627906514` Project Zombalanced - Traits and Occupations, `3802917504` Definitive Descriptions (Occupations, Moodles, Skills & Traits + Mod Support!).

Three distinct collisions here, and they are not the same:

1. **Runtime trait add/remove contention.** § 4.5 adds and removes the night-vision and short-sighted traits server-side with an ownership flag "so a natively held trait is never removed", then calls `sendSyncPlayerFields(player, 2)`. ETW and Dynamic Traits do the same for their own traits. **The ownership flag protects us from removing their traits; nothing protects us from them removing ours.** A mod that rebuilds a character's trait list wholesale will drop a mod-granted trait, and the mod will then re-add it on the next grade evaluation, producing a flicker and a packet per cycle. **Stance: needs a compat rule in the mod** — re-assert owned traits on every slow tick rather than only on grade change, which makes the flicker self-healing and costs one list read per player per minute.
2. **The band traits.** The library already records that the player-stats packet does not carry the band traits (`nutrition-mp-sync`). Any trait mod that pushes its own trait sync competes for the same packet.
3. **`SomewhatTraitsCore` is a direct macro rival** and it is *installed and read here*, so it is the one testable trait collision: its `SWAdaptiveMetabolism` handler writes player calories on `OnTick` to hold body weight in a band. Under takeover the mod owns body composition and the calorie store; that handler will fight it every tick. **Stance: incompatible-and-say-so for that one trait**, and it is the cheapest live experiment in this note, because both mods' code is readable on this machine.

**Stance for the family overall: coexists as designed for trait *definitions* (a new trait with a cost is inert against the nutrition model), needs a compat rule for trait *systems* that mutate the list at runtime** (ETW, Dynamic Traits, Somewhat Traits). Name ETW and Dynamic Traits in the release notes; test against Somewhat Traits because it is here.

## Shortlist to subscribe and read

Five, ranked, each with the one question the read must answer. Every one of these is a question no Workshop page can settle.

1. **`3690404044` Nutrition Makes Sense [2.0]** (7 729 subs, updated the day before this read) — **Does it register `Hook.CalculateStats`?** If yes, ruling 5's wall is not hypothetical: the largest nutrition mod on the Workshop already owns the hook, and a public release must ship the overlay mode as a first-class documented configuration rather than an escape hatch. If no, we learn how a 7 700-subscriber mod overrides hunger without the hook, which is the overlay design's reference implementation. Second question if budget allows: how it injects its button into the health panel, since that is the same seam § 4.7's character-info tab uses and the Wounds Overhaul conflict shows how it breaks.
2. **`2997722072` StatsAPI** and **`3415375593` Stat Tweaks Lib** (read as one item) — **Does either claim `Hook.CalculateStats`, and does either publish a registration API other mods use to change stats?** This decides whether the hook is a one-claimant resource in practice or a contested one, and it is the gate on ruling 5. A published registration API would also be worth consuming rather than competing with.
3. **`3736275816` ApocalipseBR - Nutrition Sync Fix** — its page answered the *what* (see its entry: the client’s non-decaying calorie counter is pushed to the server on every eat, so weight only rises), so the remaining question is narrower and purely mechanical: **which call does it use to apply the server’s authoritative macros on the client, and does that write stick across the next engine push?** That is the same question the spec’s client mirror must answer in reverse, and this is the only published implementation to compare against. Its page read shrank this from an open question to a mechanical one, which is why it now sits below the two hook questions; it remains the cheapest useful code read of the six.
4. **`2914075159` Evolving Traits World (ETW)** — **When it re-evaluates a character's traits, does it rebuild the list or mutate it, and does it call `sendSyncPlayerFields`?** If it rebuilds, it will drop the mod's night-vision and short-sighted grants and the "re-assert every slow tick" rule becomes mandatory rather than defensive. Its trait-sync call is also the only public example of the packet path § 4.5's trait toggles depend on.
5. **`3694097672` Tooltiplib — Tooltip Framework for Modders** — **Is it a usable optional seam for appending tooltip lines, and does it own the height arithmetic?** If yes, § 4.7's tooltip wrap should detect and consume it exactly as it detects MoodleFramework, and the ten-plus tooltip mods stop being a compatibility surface. This is the cheapest of the five and the one most likely to *remove* work.

Two near-misses worth naming, not in the five: **`3785515388` Reasonable Nutrition** (the cheapest possible read of a rival item pass, 145 KB, but the compatibility answer is already known — load order) and **`3809133438` Realistic Hunger (Prototype)** (days old, a direct rival on the same model; worth watching rather than reading, because a prototype's code will not be its release code).
