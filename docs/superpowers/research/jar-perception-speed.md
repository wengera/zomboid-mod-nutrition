Every cite is `Class.method @off L<n>` taken from a `pz.sh dump` in front of the reader; every absence is a
jar-wide `pz.sh grep` that printed `no class contains that literal` (cap `--max 60`, never reached).
Exposure verdicts are membership in the class set dumped from `LuaManager$Exposer.exposeAll()` (965 distinct
`zombie/*` classes on this build), read whole.

## Summary for the design

The engine has no single "perception" number: it has four unrelated computations, and only two of them are reachable by moving a stat.
The rendered view cone is `LightingJNI.calculateVisionCone`, a degrees value built from fatigue, the Drunk and Panic moodle levels, room/luma, the Eagle Eyed and Night Vision traits and the worn-item vision multiplier — and `LightingThread.create` returns immediately on a dedicated server, so that whole computation is client-only and the mod can only steer it by moving its inputs.
"Dark vision" does not exist under that name; the mechanism is the trait `CharacterTrait.NIGHT_VISION` (the trait the wiki calls Cat's Eyes), which adds `36 × (1 − dayLightStrength)` degrees, so it is worth the most at night and nothing at noon — exactly the shape a vitamin-A effect wants.
View *distance* is not a settable field at all: the only thing that reaches the native lighting is a boolean, `hasTrait(SHORT_SIGHTED)`, handed to `LightingJNI.playerSet`, so the mod's only lever on sight distance is toggling that trait.
The server has its own, separate perception model — `ServerLOS$LOSThread` calls `IsoGameCharacter.calculateVisibilityData` and `IsoGridSquare.CalcVisibility` — whose cone is a cosine threshold moved by fatigue, intoxication, Panic and Eagle Eyed, and whose hearing-reveal arm is gated off on the server and so never runs.
Hearing is one public getter, `IsoGameCharacter.getDetectionRange`, base 3.5 tiles, Keen Hearing +3, Hard of Hearing −1, scaled by the worn-item hearing multiplier and then reduced by the raw fatigue and intoxication stats; there is no setter anywhere in the jar.
So for both vision and hearing the only stat-shaped levers a mod has are `Stats.set(CharacterStat.FATIGUE, …)`, `INTOXICATION`, the Drunk/Panic moodle levels, the worn-item `visionModifier`/`hearingModifier` script values, and the trait list — and fatigue and intoxication both ride the once-a-second player-stats packet, so a server-side write of either reaches the client and the client's rendered cone follows.
Movement speed is the opposite story and the best news in this reading: a multiplayer client does not compute its own walk speed at all — `IsoPlayer.calculateWalkSpeed` branches on `GameClient.client` and simply copies `NetworkPlayerAI.walkSpeed`/`runSpeed` into the `WalkSpeed` animation variable, and those two floats arrive from the server in `PlayerInjuriesPacket`, pushed per player about every 2000 ms by `NetworkPlayerManager.update`.
The server-side formula is `IsoGameCharacter.calculateBaseSpeed` + `calculateWalkSpeed`: base 0.8 less 0.15 per Endurance moodle level and 0.15 per Heavy Load level, torso/neck injuries, thigh pain, bag load, wet or sandy ground, then `fullSpeedMod`, the Sprinting perk, foot injury, the thermoregulator movement modifier and tree slow factor — and no nutrition quantity enters any of it.
Two classic Lua speed levers are dead on this build: `IsoGameCharacter.setSpeedMod` is public but no player code path reads `speedMod` (only `IsoZombie` does), and `IsoPlayer.setMoveSpeed`/`getMoveSpeed` have no caller anywhere in the jar — so the honest movement lever is a server-side write to the `WalkSpeed`/`RunSpeed` animation variables (or to their inputs) inside the 2 s window before the next push.
Combat speed is client-authoritative: `CombatManager.pressedAttack` computes `calculateCombatSpeed` only for the local player on a client, stores it via `IsoPlayer.setCombatSpeed`, and the value travels **client → server** as the `combatSpeed` field of `zombie/network/fields/hit/Player` inside the hit packets, where `process()` writes it back as the `CombatSpeed` animation variable on the receiver.
`calculateCombatSpeed` already answers to the Endurance and Heavy Load moodles (−0.07 per level each) and to the thermoregulator, so a nutrition mod that drives those moodles moves swing speed for free; `setMeleeDelay`/`getMeleeDelay` on the other hand have no reader in the jar at all and are not a lever.
The "reaction" surface that is really settable is `IsoGameCharacter.setAimingDelay` — public, exposed, and read by `CombatManager.calculateHitChanceData` through `getAimDelayPenalty` — but `CombatManager.setAimingDelay` recomputes it from the weapon after every shot, so a mod scaling it has to re-apply.
Dynamic traits do sync, and this overturns the library's standing claim: `SyncPlayerFieldsPacket` param bit `2` writes `CharacterTraits.write` and reads `CharacterTraits.read`, the read doing a full `reset()`-then-`add()` replace keyed on each trait's `Registries.CHARACTER_TRAIT` resource location, so a mod-registered trait travels too.
The trigger is a Lua global: `LuaManager$GlobalObject.sendSyncPlayerFields(IsoPlayer, byte)`, gated on `GameServer.server`, and `INetworkPacket.send(IsoPlayer, …)` delivers to that one player's own connection only — so toggling Night Vision or Short Sighted server-side and calling `sendSyncPlayerFields(p, 2)` is a working route to a perception effect, but it reaches only that player's client and no one else's copy of them.
Two side findings worth carrying: clothing run-speed penalties are computed by `calcRunSpeedModByClothing`, which has no caller in the jar and is only drawn in the tooltip, so on this build clothing shows a speed penalty it does not apply; and shove/melee critical chance already reads the *target's* `Nutrition.getWeight()`, the only place nutrition touches combat today.
Nothing here was run: every side verdict below is a readable branch, and whether a given host reaches it is a question for the harness.

`calculateVisionCone`, non-vehicle arm, in order: start `144.0` (`@18 L462`); subtract `72.0 × Stats.get(FATIGUE)` (`@22–@37 L463`); cap at `144.0` (`@39–@50 L464–L465`); subtract `36.0` if `Stats.isAtMaximum(FATIGUE)` (`@51–@69 L468–L469`); if `Moodles.getMoodleLevel(DRUNK) >= 2` subtract `0.36 × Stats.get(INTOXICATION)` (`@70–@100 L472–L473`); if `getMoodleLevel(PANIC) == 4` subtract `36.0` (`@101–@120 L476–L477`); lerp the private static `lumaInvertedLerp` toward `getLumaInverted` at rate `0.1` and subtract `126.0 × lumaInvertedLerp` in a room, else `126.0 × min(1 − dayLightStrength, lumaInvertedLerp)` (`@121–@188 L480–L489`); `PZMath.clamp(18.0, 180.0)` (`@189–@199 L493`); add `36.0 × dayLightStrength` if `hasTrait(EAGLE_EYED)` (`@200–@217 L495–L496`); add `36.0 × (1 − dayLightStrength)` if `hasTrait(NIGHT_VISION)` (`@218–@235 L498–L499`).
Vehicle arm: start `324.0`, subtract `540.0 × (1 − dayLightStrength)`, the same fatigue-max, Drunk and Panic terms, the same `NIGHT_VISION` bonus, and a floor of `36.0` when the headlights are on and can emit (`@239–@370 L503–L523`).
Both arms then multiply by `getWornItemsVisionMultiplier` (`@371–@377 L527`), `PZMath.clamp(18.0, 360.0)` (`@378–@388 L530`), lerp into `visionConeLerp` at rate `0.033` (`@389–@415 L533–L534`) and return `degreesToCone(visionConeLerp)` (`@415–@421 L537`).
Because `visionConeLerp` is a `private static`, the lerped cone is one value per process, not per character — a second reader of the same method in the same frame moves it.

`calculateVisibilityData` (the server's cone) is a cosine threshold, not degrees: `f = max(0, FATIGUE − 0.6) × 2.5` (`@0–@23 L17765–L17766`); `cone = −0.2 − f` (`@24–@29 L17767`); a further `−0.2` when `f >= 1` (`@33–@43 L17769–L17770`); `− INTOXICATION × 0.002` when `getMoodleLevel(DRUNK) >= 2` (`@44–@81 L17772`); `−0.2` when `getMoodleLevel(PANIC) == 4` (`@82–@100 L17774–L17775`); `+0.2` when `hasTrait(EAGLE_EYED)` (`@101–@118 L17777–L17778`); forced to `1.0` for an `IsoPlayer` in a vehicle (`@119–@134 L17780–L17781`).
`CalcVisibility` computes `dot = normalize(playerPos − squarePos) · lookDir` (`@265–@273 L9482`) and marks the square visible on the branch where `dot > cone` is **false** (`@377–@398 L9499–L9501`, the `bCouldSee(true)` arm at `@679 L9535`) — so a **higher** `getCone()` is a **wider** cone, and the vehicle value `1.0` is 360°.
Inside `CalcVisibility` the hearing-reveal arm is gated `if (!GameServer.server)` (`@285 L9487`) and the ambient/lighting arm is skipped when `GameServer.server` (`@419 L9502`); since the method's only caller in the jar is the server LOS thread, the hearing-reveal arm is not reached on any traced path.

## Not read

- The native side of the lighting bridge. `LightingJNI.playerSet` is the boundary; what the native code does with the Short Sighted boolean, the effective fatigue and the detection range — and therefore what "sight distance" numerically is — is outside any bytecode read. A live run with the trait toggled is the only way to price it.
- Cadences other than the two constants quoted. The 2000/1000/500 ms update limits came off `NetworkPlayerManager.<clinit>`; how often `updateInternal2`, `updateMovementRates`, `updatePlayer` or the server LOS thread actually run on a session was not established, and by [the jar-research rule](../../platform/jar-research.md#walls) that is a run question.
- The animation side of `WalkSpeed`, `RunSpeed`, `CombatSpeed`, `FitnessSpeed`, `StrafeSpeed` and `WalkSpeedTrees`. These are animation variables; how the animation system turns them into a movement rate or a swing duration lives in the shipped animation data, not the jar, and was not opened.
- Whether the shipped `media/lua` calls any of the dead members. The absence claims above are absences of *Java* callers; `setMoveSpeed`, `setSpeedMod` and `setMeleeDelay` could still be called by vanilla or workshop Lua, which this reading did not scan.
- `CharacterTrait.get(ResourceLocation)` behaviour for a name the receiving side has not registered. The trait read resolves names through it; whether an unknown name returns null, throws, or is silently dropped was not dumped, and it decides whether a mod-registered perception trait can be synced safely.
- The `CharacterTrait` registry contents. Which traits exist on this build, their script definitions, their costs and their mutual exclusions were not enumerated; only the five perception-relevant constants (`EAGLE_EYED`, `SHORT_SIGHTED`, `NIGHT_VISION`, `KEEN_HEARING`, `HARD_OF_HEARING`, plus `DEAF` and `ADRENALINE_JUNKIE`) were located.
- `IsoPlayer.calculateIdleSpeed`, `calculateInTreesSpeed`, `getArmsInjurySpeedModifier`, `getFootInjurySpeedModifier`, `calculateInjurySpeed`, `calcFractureInjurySpeed`, `calculateSneakLimpSpeedScale` and `getSlowFactor` were named in the chain but not dumped; each is a further multiplier whose own inputs are unread.
- `Thermoregulator.getMovementModifier` and `getCombatModifier` were read as call sites only. Both are multipliers on movement and combat speed and both plausibly answer to body state, which makes them a candidate nutrition lever this reading did not open.
- The rest of `IsoPlayer.updateLOS` (648 instructions) and the whole of the client-side visibility polygon (`VisibilityPolygon2$Drawer`). The client's own path from the cone to what it draws was followed only as far as `playerSet`.
- `RenderSettings$PlayerRenderSettings.getViewDistance` and `ClimateManager.setViewDistance`. Both name a "view distance" and neither was investigated; they are a render option and a fog parameter respectively on the face of it, but that was not confirmed.
- Access flags were parsed with a scratch parser rebuilt from the toolchain's own constant-pool module in this session, per [the access-flag rule](../../platform/jar-research.md#method); the parser was not kept, so every flag above is only as fresh as this reading.
