## 1. The combat stance

**Holding it.** `setForceAim(Z)` is a default method of the interface `CharacterInputComponentEntity`, which `IsoPlayer` implements, and stores the flag on the input component (`CharacterInputComponentEntity.setForceAim @0–@18 L32–L33`, `CharacterInputComponent.setForceAim @0–@5 L98–L99`); a jar-wide grep finds `setForceAim` named only in those two classes and `IsoPlayer`, and `toggleForceAim` likewise. Every update, `IsoPlayer.UpdateInputState` sets the input's aiming from an aim key (`@110–@136 L4350`), clears the force-aim when the input runs or sprints (`@359–@375 L4393–L4394`), and with the force-aim on sets the input's `isAiming` and `isCharging` true (`@378–@392 L4397–L4399`):

```
    359  L4393  aload_1 / InputState.isRunning / ifne 373 ; aload_1 / getfield InputState.sprinting / ifeq 378
    373  L4394  aload_0 / iconst_0 / invokevirtual IsoPlayer.setForceAim
    378  L4397  aload_0 / invokevirtual IsoPlayer.isForceAim / ifeq 395
    385  L4398  aload_1 / iconst_1 / putfield InputState.isAiming
    390  L4399  aload_1 / iconst_1 / putfield InputState.isCharging
```

`updateInternal2` copies it into the character (`@1709–@1717 L2580`, `setIsAiming(inputState.isAiming)`), stops the queue's aim-stoppable actions (`@1746–@1754 L2586–L2587`, `StopAllActionQueueAiming`), and while aiming sets moving, running and sprinting false (`@1771–@1790 L2596–L2599`). So a mod holds the stance by re-asserting `setForceAim(true)` from `OnPlayerUpdate` every frame (section 9: the input component's frame step clears it every frame while the option toggle-to-aim is off) and walks in it; a run or a sprint key drops it. The release is vanilla's own call, `nullifyAiming()` (`IsoPlayer.nullifyAiming @0–@22 L1153–L1157`: the force-aim toggled off and aiming cleared; `lua:lua/shared/TimedActions/ISFitnessAction.lua:15 "self.character:nullifyAiming()"`). A hit reaction clears aiming but not the force-aim (`PlayerHitReactionState.enter @29–@31 L34`, #4293), so the stance resumes when the reaction exits [#4332/C/C-only].

**Moving in it: the backpedal.** An aiming character outside a path strafes: `IsoGameCharacter.isStrafing @0–@23 L1195–L1198` is the path's strafe flag or `isAiming()`. `updateMovementFromInput` takes the facing from the aim vector when it is non-zero and else from the move vector (`@94–@101 L3017`, `@185–@277 L3032–L3040`), but on the strafe branch (`@334–@338 L3050`) it never calls `setForwardDirection(playerMoveDir)`, which only the non-strafe branch does (`@474–@511 L3070–L3074`); and `updateInternal2` applies the move facing only when not aiming (`@3087–@3111 L2818–L2819`). The aim vector is zero unless an aim key is down (`IsoPlayer.getAimVector @0–@19 L1743–L1747`, `isAnyAimKeyDown`), and with a key down it is the reticle's (the mouse's) direction (`calculateAimVector @0–@65 L1751–L1757`, `AimingReticle.getX/getY`); the firearm-only `setAngleFromAim` runs only for an aimed firearm (`IsoGameCharacter.updateInternal @2197–@2235 L9370–L9372`). So under a force-aim with no key down, a melee character keeps the facing a `faceThisObject`/`faceLocationF` gave it and moves along the auto-walk vector: walking away from the zombie it faces is the backpedal [#4332/C/C-only].

**Its speed and cost.** While aiming, `IsoGameCharacter.calculateWalkSpeed @227–@307 L10097–L10102` sets the animation variable `StrafeSpeed` to 0.8 × max(0.48, min(0.9 + Nimble / 10, 1.5) × min(2.5 × the walk speed, 1)), the speed scale the strafe nodes play at (`lua:AnimSets/player/strafe/strafeDefault.xml:6 "<m_SpeedScale>StrafeSpeed</m_SpeedScale>"`, whose backward blend `Bob_WalkBwdAim1Hand` sits at `m_SpeedScale` 0.80); and `updateInternal2 @2142–@2175 L2671–L2676` multiplies the local move rate by 0.7 when the aiming player just moved and by its nimble modifier. A caller scan of `isAiming` over `IsoPlayer`, `IsoGameCharacter`, `Stats`, `BodyDamage` and `Metabolics` finds no read in `updateEndurance` or any stat update, so the stance itself costs nothing beyond the walk; it does skip the auto-drink (`IsoGameCharacter.autoDrink @74 L11771`) [#4295/C/C-only].

**The swing and the shove from it.** `DoAttack` is the same call aiming or not (#4292); `CombatManager.pressedAttack` takes the attack as unarmed, a shove, when `isDoShove()` reads true (`@159–@176 L3212`), the flag the melee key sets in `updateInternal2` (`@2342–@2344 L2707`, `setDoShove(true)`) (`setDoShove(Z)` is declared on `IsoLivingCharacter`).

**Rule:** a force-aim set by `setForceAim(true)` lasts one frame while the option toggle-to-aim is off, because the input component's frame step clears it before the next update, so a mod re-asserts it from `OnPlayerUpdate` every frame, where the same update's `UpdateInputState` reads it; a run or a sprint key clears it, and while it holds the character walks only and keeps the facing the mod gave it, so the auto-walk vector moves it while it faces its target [#4332/C/C-only].

**Proposed `aim {targetId|bearing, vx, vy, seconds}` (PZA/1.5, Tasks 9 and 10).** At start: `MO.want("walk")` (a run latch would clear the force-aim) and `p:setForceAim(true)`. Per tick: face (`p:faceThisObject(z)` for `targetId`, else `p:setForwardDirection(cos b, sin b)` for `bearing`), then the steer path's own `setAutoWalk(true)` and `setAutoWalkDirection(<input-space vector>)` for `(vx, vy)` (zero for a standing fight). The `attack` skill swings unchanged inside it (`DoAttack(0)` after the face); a shove is `p:setDoShove(true)` then `DoAttack(0)`. At end, supersede or stop: `p:nullifyAiming()` and `MO.off`. The path follower will not climb while aiming (#4289), so `walkTo` and `climb` release the stance first.

Not read: whether the auto-walk vector drives a strafe the same as the keyboard's (`getInputMoveVector @32–@55 L4323–L4327` reads it; the strafe branch's `ipX/ipY` use is not followed); where the `0.7 × nimble` move rate lands; the shove's own reach and when `doShove` is cleared; the swing's hit direction (`attackCollisionCheck`).

## 2. The climb and the vault

**The short fence.** `climbOverFence(dir)` (#4289: a current square, the window helper, `isPlayerAbleToHopWallTo`) sets `ClimbOverFenceState`'s parameters, which record the character's running and sprinting at that moment (`ClimbOverFenceState.setParams @336–@361 L712–L713`) and the far square's counter (`solidtrans`), floor and sheet rope (`@135–@197 L696–L698`, `@300–@333 L709–L711`). On entry (`enter @26–@119 L99–L104`, and `processOnEnter @0–@72 L738–L741` alike) a run takes `runningEnduranceReduce` × 300 endurance and sets `VaultOverRun`, a sprint × 700 and `VaultOverSprint`; a walk takes none. The outcome is `success`, or `obstacle` over a counter (`@120–@172 L108–L113`), `falling` with no floor beyond (`@260–@284 L129–L130`), `rope` onto a sheet rope (`@285–@311 L133–L134`), and `fall` only on a vault: `@182–@216 L116–L118` asks `shouldFallAfterVaultOver` only when `VaultOverRun` or `VaultOverSprint` is set [#4296/C/C-only]:

```

    200  L117  aload_0 / aload_1 / invokevirtual ClimbOverFenceState.shouldFallAfterVaultOver / ifeq 217
    208  L118  aload_1 / 'ClimbFenceOutcome' / 'fall' / setVariable
```

**The vault's trip.** `shouldFallAfterVaultOver @0–@267 L566–L608` sums a chance: 10 on a sprint, then 10 per endurance moodle level, 10 per drunk level, 13 per heavy-load level, 5 per pain level, the lower torso's additional pain over 20 divided by 10, 10 for Clumsy, −10 for Graceful, 20 and then 10 more for Very Underweight (the bytecode tests `VERY_UNDERWEIGHT` twice, L593 and L596), 20 for Obese, 10 for Overweight, minus the Fitness level; the vault falls when `Rand.Next(100)` is under it (`@251–@267 L608`). A fresh character at a run (no moodles, Fitness 5) has a chance of −5 and never falls; at a sprint, 5 in 100. The fall plays `FallenOnKnees`/`VaultSprintFallLanded` (`OnAnimEvent_FallenOnKnees @0–@4 L412–L413`, `OnAnimEvent_VaultSprintFallLanded @0–@8 L416–L418`, the second dropping the hand items first), and `IsoGameCharacter.fallenOnKnees(Z)` (which returns on a client, `@0–@6 L14844–L14845`) dirties four random parts and then, with chance 1 in 4 + Nimble (`@164–@179 L14873–L14874`; `RandInterface.NextBool(I) @0–@15 L32` is `Next(n) == 0`), drops the hand items 1 time in 4, holes the clothing over one random part, and unless `Rand.Next(100)` falls under that part's clothing defence (`@227–@236 L14886`) bloodies it and gives a deep wound on a part already scratched (`@247–@255 L14889–L14890`) or a scratch [#4296/C/C-only]. The free-movement vault is the only path to a run climb that a walk does not choose: `checkVaultOver` needs a run or a sprint (#4289), and a path climb records whatever gait the follower walked at.

**The tall fence.** `IsoPlayer.climbOverWall(dir) @0–@32 L6159–L6167` refuses unless `canClimbOverWall(dir)`, drops the heavy items, and sets `ClimbOverWallState` going; vanilla's timed action picks it for an item whose `isTallHoppable()` holds (`lua:lua/client/TimedActions/ISClimbOverFence.lua:28 "if self.isTallHoppable then"`). `ClimbOverWallState.enter @10–@61 L60–L67` takes `runningEnduranceReduce` × 1200 endurance and × 500 more on a struggle. The roll is `ClimbOverWallState.setParams @197–@388 L344–L370`, for the local player: with the `EasyClimbing` sandbox option always success; otherwise s = `getClimbingFailChanceInt()`, the struggle is `NextBool(s / 2)`, and the climb succeeds when s > 0 unless `NextBool(s)` (chance 1 − 1/s), and at s ≤ 0 only without a heavy-load moodle, when `Rand.Next(100)` ≤ max(1, Strength). The score (`IsoGameCharacter.getClimbingFailChanceFloat @0–@305 L17433–L17474`, truncated by `getClimbingFailChanceInt @0–@4 L17429`) is the integer square root of max(0, x), where x = 2 × (Fitness + Strength + Nimble), − 5 per endurance level, − 8 per drunk level, − 8 per heavy-load level, − 5 per pain level, − 25 Obese or else − 15 Overweight, then halved for Clumsy and halved for awkward gloves (+ 4 for other gloves), − 4 All Thumbs or else + 4 Dextrous, + 4 Burglar, + 4 Gymnast, and finally + `nearbyZombieClimbPenalty()` [#4297/C/C-only]. A fresh character (Fitness 5, Strength 5, Nimble 0) has x = 20, s = 4: a 1 in 4 failure and a 1 in 2 struggle.

**The drag-down's twin.** `nearbyZombieClimbPenalty @0–@96 L17478–L17493` walks the moving objects on the character's own square and adds 25 for each zombie whose `target` is the character in `AttackState` and 7 for every other zombie there: the same targeting-and-attack-state test as the drag-down's count (#4290), on one square, and it raises the score, so a zombie at the character's back makes a tall climb likelier to succeed, not less [#4297/C/C-only].

**What a mod calls.** Vanilla walks adjacent and queues the timed action (`lua:lua/client/ISUI/ISWorldObjectContextMenu.lua:2351 "ISTimedActionQueue.add(ISClimbOverFence:new(playerObj, fence, direction))"`), which faces the edge in `waitToStart`, picks the direction from the fence square's `HoppableN` and the character's side (`ISClimbOverFence.lua:43–59`), and calls `climbOverWall` or `climbOverFence` in `perform` (`:26–35`); it is `stopOnWalk`, `stopOnRun` and `stopOnAim` false (`:66–68`).

**Rule:** a short fence climbed at a walk costs no endurance and has no fall roll; only a climb begun at a run or a sprint (the vault) costs `runningEnduranceReduce` × 300 or × 700 and rolls the trip, whose landing wounds 1 time in 4 + Nimble; a tall fence costs × 1200 and fails 1 time in s [#4296/C/C-only] [#4297/C/C-only].

**Proposed `climb {x, y}`.** The fence's square `(x, y)` and the character's side give the edge; the skill walks to the near square at a walk (`MO.want("walk")`, the stance released), finds the fence object on the square (the object whose `isHoppable()` or `isTallHoppable()` holds; `IsoObject.isHoppableOrWindowFrame`, #4288's reading), and queues `ISClimbOverFence:new(p, fence, nil)`; done when the character's square is the far square, failed when the action ends without it (a tall fence's `fail`). The planner's instinct: prefer a walk climb to a vault, never vault (no run into a hoppable edge) unless the threat rule says flee, and treat a tall fence as a 1 in s gamble at s read from the frame through `getClimbingFailChanceInt()` (its exposure to Lua not checked).

Not read: the climb clips' durations; what a failed tall climb does (`ClimbOverWallState.exit`/`animEvent`); `canClimbOverWall`'s conditions; the scratch flag `SCRATCH` (set false at `setParams @289–@297 L708` and not followed); the `obstacle`/`falling` outcomes' effects; whether `ZomboidGlobals.runningEnduranceReduce` is `defines.lua`'s `RunningEnduranceReduce = 0.0000520` (`lua:lua/shared/defines.lua:5`), which is inference from the name.

## 3. The bandage

**What it does.** `BodyDamage.SetBandaged(int, boolean, float, boolean, String) @0–@20 L1904–L1905` is `BodyPart.setBandaged(boolean,float,boolean,String)`, which on `true` clears the part's `bleeding`, `bitten`, `scratched`, `cut`, `stitched` and `deepWounded` flags (the wound times kept), sets the alcoholic flag and the bandage type, and on both branches the life and `bandaged` (`@0–@163 L663–L700`); on `false` it re-raises each flag whose time is still above zero (`@60–@141 L677–L693`).
`BodyPart.DamageUpdate`, which returns at once on a client for a local player (`@0–@30 L154–L155`, so it runs on the server), then treats a bandaged part differently (`@31–@250 L158–L182`, `@615–@771 L230–L249`) [#4298/C/C-only]:

| drain or decay, per update × `GameTime.getMultiplier()` | unbandaged | bandaged |
|---|---|---|
| deep wound (`applyDamage`, × the part's `damageScaler`) | 3.125 | 1.5625 |
| scratch / cut / bite (`applyDamage`) | 0.9375 / 1.875 / 2.1875 | none |
| bleeding, from general health (`ReduceGeneralHealth`, fires `OnPlayerGetDamage` `BLEEDING`) | 0.2857142984867096 × scaler × bleedingTime / 10 | none |
| bleeding time | − 0.00002 | − 0.0002 |
| bandage life while the part bleeds | — | − 0.0003 (− 0.005 with a deep wound) |

The bleeding flag clears when the bleeding time falls below 0 (`@755–@771 L247–L249`). A bandage whose life has reached 0 still reads `bandaged`, so it still stops the drains; `isBandageDirty()` is `getBandageLife() <= 0` (`@0–@14 L150`).

**The infection roll.** `DamageUpdate @774–@1013 L254–L304` rolls a wound infection for a part not already infected and not under an alcoholic bandage with life above 0 that has a deep wound, scratch, cut or stitch: once per update, `Rand.Next(Rand.AdjustForFramerate(n)) == 0` sets `infectedWound`, where n starts at 40000 (`@840 L256`) and loses 10000 unbandaged, or 35000 under a bandage whose life is exactly 0 (`@860–@873 L259–L260`), 20000 for a scratch, 25000 for a cut, 30000 for a deep wound, 24000 for glass, 23000 for a burn, 7000 for a burn needing a wash, 20000 for one further test at L293, 24000 for bloody clothing, and is floored at 5000 (`@988–@997 L300`). The decrements after L259 are `wide iinc` constants decoded by hand (the dumper mis-steps them); L260's `ldc_w 35000` prints cleanly. So a clean bandage on a scratch leaves 1 in 20000, no bandage 1 in 10000, and a dirty rag (life 0) 1 in 5000 [#4299/C/C-only].

**The vanilla action.** `ISApplyBandage` sets the life to a random float between (Doctor + 1) × 0.5 and (Doctor + 1) plus the item's `BandagePower`, or 0 for an item whose type contains `Dirty` (`lua:lua/shared/TimedActions/ISApplyBandage.lua:112 "local bandageLife = ZombRandFloat((self.doctorLevel + 1) * 0.5, (self.doctorLevel + 1) * 1.0) + self.item:getBandagePower();"`, `:113`), calls `SetBandaged` with the item's `isAlcoholic()` and full type (`:119`), removes the item (`:120`), infects the part when the item is infected (`:125–:127`), and syncs the part (`:148`); it lasts 120 − 4 × Doctor ticks (`:161`) and its `new` is `(character, otherPlayer, item, bodyPart, doIt)` (`:173`), `doIt` false removing the bandage. The powers: `Bandage` and `AlcoholBandage` 4.0 (`lua:scripts/generated/items/normal.txt:8078 "BandagePower = 4.0,"`, `:8045`), `RippedSheets` and `AlcoholRippedSheets` 2.0 (`:10663`, `:8063`), `Bandaid` 1.5 (`:8125`), `RippedSheetsDirty` and `BandageDirty` 0.5 (`:10690`, `:8109`) but life 0 by the `Dirty` rule [#4299/C/C-only].

**Rule:** any bandage stops a part's bleeding, scratch, cut and bite drains and speeds its bleeding's end tenfold, and a clean one halves the infection odds against none, while a dirty one doubles them [#4298/C/C-only] [#4299/C/C-only].

**Proposed frames and `bandage {part|worst, itemId}`.** The frame's `body.parts[]` carries, per part, `bleeding()`, `getBleedingTime()`, `bandaged()`, `getBandageLife()`, `isBandageDirty()`, `isInfectedWound()` and the four wound times; `worst` is the part with the largest bleeding time among the bleeding, unbandaged parts, then a dirty-bandaged wounded part. The skill queues `ISApplyBandage:new(p, p, item, part, true)` with the item chosen alcoholic, then clean, then dirty (a dirty rag only on a bleeding part, since it stops the drain but doubles the odds), and `ISApplyBandage:new(p, p, nil, part, false)` first to take a dirty bandage off a part that has stopped bleeding.

Not read: what `infectedWound` does to health; the L293 test's member; `applyDamage`'s unit; the deep wound's own bleeding generation.

## 4. The rip

**Which items.** The `RipClothing` craft recipe takes one item tagged `base:ripclothingcotton`, not worn, with no tool, in the dark too, over `time = 40` (`lua:scripts/generated/recipes/recipes.txt:226 "item 1 tags[base:ripclothingcotton] flags[AllowDestroyedItem;IsNotWorn;ItemCount],"`, `:217–:232`); 243 clothing items carry that tag (a count of `scripts/generated/items/clothing.txt`, among them dresses, shirts and T-shirts, e.g. `:45`). `RipDenimClothing` takes the denim and leather tags (38 denim items) and needs scissors or a sharp knife (`:242 "item 1 tags[base:scissors;base:sharpknife] mode:keep flags[MayDegradeLight;Prop1;IsNotDull],"`). `RipSheets` turns a `base:sheet` into 10 `RippedSheets` (`:282–:296`). Worn clothing is never an input (`IsNotWorn`), so no worn item is at risk; the loot keeps spare unworn cotton clothing for rags.

**The yield.** `RecipeCodeOnCreate.ripClothing @0–@311 L550–L579`: with the consumed clothing's fabric type (none → nothing), n = max(1, covered parts − holes − patches) (`@90–@108 L559`), the count is clamp(`Rand.NextInclusive(n == 1 ? 1 : 2, n)` + Tailoring / 2, 1, n) (`@110–@150 L560–L563`), and each piece is the fabric's `material`, or its `materialDirty` when `Rand.Next(99) + 1` ≤ the item's dirtiness plus blood level (`@189–@215 L567`); a clean `RippedSheets` gets `filterLife` = 1 − min(dirt + blood, 100) / 100 in its modData (`@239–@277 L569–L571`); a buckled item adds a buckle (`@293–@310 L576–L577`). Cotton's materials are `Base.RippedSheets` and `Base.RippedSheetsDirty` (`lua:lua/shared/Definitions/ClothingRecipesDefinitions.lua:7 "Base.RippedSheets"`, `:8`) [#4300/C/C-only].

**Rule:** an unworn cotton garment rips with no tool into between 1 (or 2) and its covered-part count of rags, more with Tailoring, each rag dirty with a chance equal to the garment's dirt plus blood in percent [#4300/C/C-only].

**Proposed `rip {itemId}`.** The skill refuses a worn item or one without the cotton tag, then runs vanilla's own context-menu path: `ISInventoryPaneContextMenu.OnNewCraft(item, getScriptManager():getCraftRecipe("RipClothing"), p:getPlayerNum(), false)` (`lua:lua/client/ISUI/ISInventoryPaneContextMenu.lua:3428`, which builds a `HandcraftLogic`, checks `canPerformCurrentRecipe()` and queues `ISEntityUI.HandcraftStart` at `:3468`; vanilla fetches a craft recipe by name the same way at `lua:lua/client/ISUI/ISFirearmRadialMenu.lua:465`). The handcraft lasts `craftRecipe:getTime(character) × 5` (`lua:lua/shared/Entity/TimedActions/ISHandcraftAction.lua:253–:261`), `getTime` not read.

Not read: `CraftRecipe.getTime(character)`; `getNbrOfCoveredParts` for a given garment; whether `OnNewCraft` needs the inventory UI open.

## 5. The wash

**The live path.** `ISWashClothing` turns an item with `ItemAfterCleaning` into that item: `RippedSheetsDirty` → `RippedSheets` (`lua:scripts/generated/items/normal.txt:10695 "ItemAfterCleaning = Base.RippedSheets,"`), `BandageDirty` → `Bandage` (`:8114`). It needs the source's `getFluidAmount()` at least `GetRequiredWater`, which for a non-clothing item is ceil(4 + 3 × blood level) (`lua:lua/shared/TimedActions/ISWashClothing.lua:6`, `:76–:92`), removes the item and adds the clean one (`:144–:151`), and uses that water from the source (`:172 "self.sink:useFluid(water);"`); soap is optional (`noSoap`), the time is (blood + dirt) × 15 (× 5 without soap), clamped to [100, 800] before `adjustMaxTime` (`:193–:216`), and its `new` is `(character, sink, item, bloodAmount, dirtAmount, noSoap)` (`:230`), with vanilla passing the item's blood level for a non-clothing item after walking adjacent (`lua:lua/client/ISUI/ISWorldObjectContextMenu.lua:1777`, `:1812–:1815`). **The dead path.** The menu's `CleanBandages` looks up the old recipe `Base.Clean Rag` (`lua:lua/client/ISUI/ISWorldObjectContextMenu.lua:2004`) through `getScriptManager():getRecipe` (`:1877`), and no `Clean Rag` recipe exists under 42.21's `scripts/` (a grep), so that path offers nothing [#4301/C/C-only].

**Rule:** a dirty rag becomes a clean one at any water source holding ceil(4 + 3 × its blood level) units, tainted or not, soap optional [#4301/C/C-only].

**Proposed `wash {itemId, sourceId}`** (the source an object on a square adjacent to the character): queue `ISWashClothing:new(p, source, item, item:getBloodLevel(), 0, soaps:isEmpty())` with `soaps = p:getInventory():getSoapList(nil, true)` (`:236`), after checking `source:getFluidAmount()` against the requirement. The map's water record (§ 7) is the source read.

## 6. The look

**Facing.** `faceDirection(IsoDirections) @0–@5 L10423–L10424` sets the forward direction at once; `faceLocation(x, y) @0–@14 L10427` faces the square's centre through `faceLocationF`.
**Seeing.** `IsoGameCharacter.updateSeenVisibility(I) @0–@55 L9407–L9430` stores `TestIfSeen(i, player)` in the per-player `isVisibleToPlayer` and, for an unseen non-player, sets its target alpha to 0; `TestIfSeen @0–@153 L2086–L2110` reads the character's square's per-player `isCanSee`, or `isCouldSee` within the player's detection range, past the view distance never, and then its light. `IsoPlayer.updateLOS @0–@11 L6197` clears the spotted list and zeroes `Stats.numVisibleZombies` before rebuilding them from the cell's object list by the squares' visibility (`@141–@489 L6225–L6286`) [#4302/C/C-only].
**The frames.** The agent's frames walk `getCell():getZombieList()` (`testing/PZAgent/PZAgent/42/media/lua/client/PZAgent_Sense.lua:72`), a list `updateSeenVisibility` does not filter: an unseen zombie stays in the cell and only its alpha changes. On a dedicated server, which zombies reach the client's cell is the server's replication; `UdpConnection.RelevantTo(FFF) @0–@100 L287–L294` is a positional test over the connection's areas with no facing term, and which test the zombie sender uses is not read.

**Rule:** turning changes what the client draws and spots, not what the cell's zombie list holds [#4302/C/C-only].

**Proposed:** no `look` action. **What a stomp does.** In `attackCollisionCheck` a floor shove's damage is replaced by `Rand.Next(0.7, 1.0)` + 0.2 × Strength, × 0.5 without shoes or × the worn shoes' `StompPower` (`@2590–@2663 L1023–L1029`; `Item.<init>` sets it to 1, `@395–@397 L373`; army boots carry 2.5, `lua:scripts/generated/items/clothing.txt:18769 "StompPower = 2.5,"`), before the endurance and tired multipliers (§ 11); it is not divided by arm or leg pain.
