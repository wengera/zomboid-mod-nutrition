# The moddability wall map — what a B42 nutrition mod can and cannot do

**Verified against: 42.20.4 (`b0bbce05d5`)** · 2026-09-17 · slice 13 (P2b), classified **offline**
from slices 01–12: the jar re-read today, `docs/vanilla/*`, the three teardowns, and slice 12's
seven live sessions `x121`–`x127`. Grades: **C** read from bytecode / Lua / scripts, **M** measured
on the live dedicated server + client (run id given), **W** wiki mirror (corroboration only).

## Summary

1. **What this is.** One row per capability a nutrition overhaul needs, across ten design areas,
   each classified against this build with the mechanism that decides it, the workaround if there
   is one, the residual risk, and a graded citation. 64 rows; 25 CANNOT · 22 CAN · 14 CAN WITH A
   WORKAROUND · 3 UNKNOWN. It is a map, not a work queue.
2. **What a verdict means.** A verdict is about *the platform*, not about our design: CANNOT means
   a named jar site closes it, and no amount of Lua reopens it.
3. **The biggest three walls.** `Nutrition` is a closed five-float value object and a mod-registered
   moodle is driven to level 0 every tick (A1, D1) · neither stats wire has a seam — `ItemStatsPacket`
   is seven members and `PlayerStatsPacket.write` is an unconditional full snapshot (E1+E2, E7+E12) ·
   every loaded script file feeds one MD5 the server compares, so a script mismatch is a **disconnect**,
   not a silent degrade (J3).
4. **The biggest three doors.** A partial `item` block **merges per key** and an unrecognised key
   becomes default modData, so the item pass ships minimal blocks that carry their own nutrients
   (J1, A5) · the eat path is interceptable **server-side before vanilla's numbers land** (B2) ·
   vanilla nutrition switches off at the sandbox, and vanilla leaves diet *quality* completely
   empty — protein has no reachable effect at all (A8, A2+A7).
5. **What it is bounded to.** 42.20.4 on a **dedicated server** with one client, one fixture, one
   admin character. Single-player is never claimed. Most M rows are n = 1 session; every bound that
   matters is written into the row that carries it, and § What the library cannot yet measure holds
   the evidence limits that are not any row's property.

## How to read this map

- **CANNOT** — the platform closes it. The Mechanism cell names the **jar site**. Any door nearby is
  a *different* capability and the cell points at its row.
- **CAN** — a mod can do it on this build, in MP, by the mechanism named. Residual risk reads `—`
  only where there genuinely is none.
- **CAN WITH A WORKAROUND** — reachable only through the named workaround, which carries a named
  residual risk. Both cells are always filled.
- **UNKNOWN** — nothing in the library decides it. The row ends `-> X<N>`, naming the experiment in
  § Named experiments that would.
- **A `+` in a row id fuses two rows, never two verdicts.** `B4+B5`, `D2+D3`, `H5+H6` and the rest
  each cover two capabilities that share **one** verdict, and the Mechanism cell names **both**
  mechanisms — splitting them back out changes the row count and nothing else.
- **`Ev` grammar:** `<grade> · <slice> · <jar site, or run id + artifact key>`, grade first and
  standalone. A run id plus a key is preferred to a paragraph; where another document owns the
  canonical prose — `patterns.md`, `anatomy.md`, `item-overrides.md`, `lua-api.md`, `docs/vanilla/*`,
  the teardowns — this map **links and does not restate the numbers**.
- **The bound on every verdict below: 42.20.4, on a dedicated server.** Single-player is not claimed,
  and where a reading is one-sided the row says which side it was taken on.

**The three viable shapes for mod state, and the rows their hazards attach to.**

1. **Server-side mutation over the command bus** (`sendClientCommand` → validate → mutate →
   `sendServerCommand`). One owner, no wipe, no packet dependency. Hazards: **E7/E8** — neither push
   direction exists for stats or item fields, so every write must originate on the server; and E11's
   namespace collision.
2. **Player modData with an explicit transmit.** Durable and saved by the engine. Hazards:
   **E9/E10** — the transmit is whole-table wipe-and-replace in both directions and it is *somebody
   else's* call, so the mod that loses the data is never the mod that transmitted.
3. **Accepting client-only semantics** (derive on the client from packet-carried inputs). Cheap and
   desync-free *while every input is carried* — which the weight-band traits are not (G4), and which
   `thirstChange` and any zero-valued conditional field are not either (E4, E5).

## What the library cannot yet measure

These are evidence limits, not verdicts. No row above rests on any of them.

- **A `-debug` client is stopped dead** by the first mod Lua error reaching `KahluaUtil.fail` — it
  parks in `UIManager.debugBreakpoint`'s modal pump. A raising mod therefore cannot be *driven* on
  the debug client, which is why I14's client half is C. A **release** client is `Core.debug`-gated
  and unmeasured; gate every raising probe on the **server** and set `[client] timeout` low.
- **`server_errors` is a classifier's output, not a fault count**, and `pzt run` reporting FAIL on a
  raising probe is the profile working as designed. No count of trace blocks is evidence of a fault.
- **Nothing on the bus executes a craft.** `recipes.craft` is a **reader**, and nothing on the bus
  reaches a right-click, so a recipe's `onCreate`/`onTest` hooks and `OnCreate` itself stay C (F1).
- **No bus route reaches an arbitrary event dispatch.** The dispatch case was measured only inside
  `EveryOneMinute` handlers on the **server** VM (`x126-20260911-045205`, `x127-20260911-052049`),
  because there is no `triggerEvent` on the bus — so what `pcall` and an unguarded raise do inside
  any *other* dispatch, and whether another mod's `pcall` fork around one changes it, is unmeasured
  (I13, I14). X26 buys exactly one such dispatch, with `ctxmenu.create` and its `event.trigger`
  sibling as the harness addition that reaches it.
- **The `getText` session carried no in-run positive control** — every reply missed — so H5+H6's
  soundness leans on slice 10's client-side `IGUI_` hit in a different session on an earlier harness
  shape. Every later session that calls `text.get` must ship an `IGUI_` control that **hits**.
- **`witness.fields` reads zero-argument getters only** and caps at 32 fields; the `Nutrition` macros
  are read through `nutrition.get`, not through `witness.fields`.
- **One fixture, one admin character, `DayLength = 4`**, and a bus cadence ceiling of
  `24 × speed / day_minutes ≲ 8` readings per game minute. **Most measured rows are n = 1 session.**
- **Artifacts older than `291f977` render floats at `%.6f`**, so no bit-level claim may rest on them.
- **modData persistence across a save/load has never been measured** (A2+A7), **the Lua drink-driver
  path has never been driven** (B7 — slice 05 measured `DrinkFluid` itself), and **no run has driven
  a deliberate client/server script mismatch** (J3).
