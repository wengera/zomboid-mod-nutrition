# The harness
Verified against 42.20.4 (b0bbce05d5) · 2026-09-30 · scope: the instrument every measured row in this library was taken with — `pzt`, the profile, the sandbox block, the driven client, the command bus and its replies, probes and witnesses, scenarios, cadence, artifact and driver discipline; the command inventory is generated into `reference/harness-commands.md` and the experiment specs are `reference/experiments.md`.

## Rules
<a id="rules"></a>

- Never read a green run as evidence that a mod loaded: the game answers a mod it cannot find with a warning and a clean boot, so the run fails fast at the server-started mark and the bus probes are what prove effect [#1793].
- Name a profile's mod by the engine-resolved id: that is the `id=` of the `mod.info` the build actually reads — the newest `42[.x[.y]]/` folder first, then `common/`, then the mod root — and never the folder name [#1558].
- Gate a probe that can stall the client on the server side: verification is asked only after the client is ready, so a stalled session's client row never runs and the run records a verification error instead of a pass or a fail [#1769/M/n=1].
- Cap the client wait in the profile whenever a probe can hang the client: the readiness wait is capped from the profile's client timeout, whose default is 300 seconds, and a profile that leaves the default sits out the full wait plus teardown — 384 seconds for a five-second hold — on a client that was never going to answer [#1768].
- Never launch a client in safe mode: it turns a seventeen-second world load into about 120, roughly seven times slower [#1711].
- Put every Java member call behind the index-first guard: a guarded call never raises and the argument-slot protected call never reaches the failure helper, while an unguarded raise, or a nested protected-call raise the mod catches, stalls the driven client, which is a -debug client that parks, and a release client raised on once answered through the raise [#1714/M/n=1].
- Take the measurement on the side that owns the quantity: for nutrition, hunger and thirst, item aging and perks the server's reading is the measurement and the client's is a once-a-second mirror [#1826].
- Ask a probe of both sides: the acceptance profile put the same trait check to the server and to the client and both returned the mod's effect, so the mod was present in both Lua states and not merely in the server's [#1825/M/n=1].
- Choose a modData exclusion set per scope and apply it to that scope and no other: an item census excludes the custom name and the tooltip, both of which vanilla writes into item modData itself [#1234/M/n=1].
- Report a member this build does not expose separately from a zero: a zero and an absent accessor are different findings, so a census reply names the members it could not read rather than leaving them silently absent, which is what keeps a false flag distinguishable from an unexposed member [#1725].
- Ask the field witness for zero-argument getters only: an arity mismatch is as fatal as a nil call, which is also why a two-call perk-experience read needs a command of its own [#1742].
- Reconcile a reply against the names that were sent and never against its count alone: the count is names read while the fields bucket is a map keyed by getter name, so their sizes add up only when every name asked for was distinct [#1744].
- Test a list for emptiness with a falsiness check or with the reply's own counts: the encoder renders an empty Lua table as an empty object, harness-wide, so a comparison against an empty array and an index both fail [#1751].
- Read the server error list rather than quoting its count: the pattern is applied to every non-indented server line that no baseline-noise pattern whitelists, so the number is a classifier's output and not a fault count [#1764].
- Keep `24 × speed / day_minutes` at or below about eight game-minutes per wall second: at the fixture's ninety-minute day and a multiplier of thirty, which is exactly eight, three runs recorded 7.99, 7.99 and 8.00 world-minutes per wall second with exactly one tick per game minute [#1814/M/n=3].
- Make every timing step a predicate with a budget and never a sleep: the world-ready barrier is a harness handshake rather than a timer [#1845].
- Record the measured window rather than the requested sleep, and name a snapshot tag by its measured offset rather than its intended one: one driver's window field read 10.0 seconds where the reads' own wall stamps give 12.54, and its tag named for three seconds after a transmit actually opened 7.58 seconds after it, so that driver's own window and tag keys are do-not-cite for exactly this reason [#1708/M/n=1].
- Copy every piece of measured evidence a document cites into a tracked per-run artifact folder as JSON, kept byte-identical: the full run directories with their logs stay local and untracked [#1705].
- Treat a scenario verdict as the test and the evaluator and a clean session together: exit code 0 needs the harness test's own pass, the evaluator's agreement and no environment fault, each of which turns the result into a failure naming its count, marks the timeline and lands in the faults block of both the report and the committed artifact [#1785].
- Read a run's exit code as a statement about the whole session and not only about the test: it is 0 only when the session had zero non-baseline server errors and no client Lua errors, the three fault reasons being a mod the game did not load, a non-baseline server error line and a client that logged a Lua error [#1702].

## How it works

<a id="pzt"></a>
### `pzt`, the orchestrator

The orchestrator ships eight commands — provision, snapshot, boot, attach, run, scenario, spike and doctor — from a roughly two-and-a-half-minute fixture provision through a fourteen-second warm boot to a one-minute run plus its hold, the costs being the harness as it stood on one machine [#1701].

| Command | What it does | Cost |
|---|---|---|
| `provision --name default` | Fresh server (`Zombies=6` = none; `--sandbox K=V` overrides), the `admin` client creates the world and its character and quits; snapshot → `testing/fixtures/default/` | ~2.5 min, once per game/mod-set version |
| `snapshot --from-run <run> --name <fixture> --parent <fixture> [--session N]` | the run's server and client caches snapshotted as a fixture whose record names its parent, run, session and lineage, so the next session boots the world the last one left (Plan 23) | seconds |
| `boot --fixture default [--hold N]` | Restore the fixture's server world into a fresh run dir and start it | ~14 s |
| `attach --fixture default --server 127.0.0.1:27261 --user admin` | Restore that user's client cache, launch, wait until in-world (no creation screens), ping | ~35 s |
| `run --fixture default [--profile <name>] [--hold N] [--clients a,b]` | boot + attach every client + hold (the test slot) + teardown + `report.json`; `--profile` adds a mod set, sandbox overrides and `[[verify]]` probes. The missing-mod fail-fast runs on the plain path too, right after `server_started`, and names the mod in the RESULT line | ~1 min + hold |
| `scenario <name> [--side server\|client] [--speed N] [--timeout S] [--fixture F] [--profile <name>]` | one registered harness test at accelerated time ([scenarios](#scenarios)); a profile's fixture wins over `--fixture` and its first client over `--user`, its probes run once the client is ready, and the cadence ceiling is checked on `DayLength` × `--speed` | ~1 min + the test (3 game-days at `--speed 30` ≈ 10 min) |
| `spike S3 S4 S5 S6 S7 [--reloadalllua]` | the design spikes as scripted experiments; findings → `runs/spike-*/findings.json` | 2–5 min |
| `doctor` | the cold-start checks of [the procedure](#procedure); exit 1 on a FAIL | seconds |

The folder-to-id rename's regression subject is the long-term-preservation mod, whose folder `SKITTLE_LongTermPreservation4220` and declared id `LongTermPreservation4220` differ by a whole prefix, so the run's mods listing names it and a wrong name would fail to load [#1657]. A case-only subject cannot answer whether the rename is required: the case-preserving filesystem lists whichever spelling the installer wrote, while case-insensitive path lookup loads the mod either way [#1656].

<a id="profiles"></a>
### The profile: one file per named combination under test

A profile is one file per named combination under test: the golden fixture to restore, the mods and where each is copied from, the sandbox overrides, the client accounts to attach, and the bus probes that must answer before the session counts as the one that was asked for [#1789]. Everything it asks for is resolved and validated before a process starts, so a bad mod id or a misspelt sandbox key costs a second instead of a boot, and any key outside the known set is a pre-boot error naming that set [#1790].
A profile never mutates the fixture: mods overlay a restored per-run copy and the sandbox block is merged into that copy's own options file, the fixture excluding the mods folder from its snapshot so the overlay is rebuilt every run [#1792]. The snapshot takes the server's configuration, database, saves and options and the client's options, saved-server database, Lua folder, saves and debug options, and leaves out the mods folder, re-installed at boot and attach so a fixture never pins a stale harness [#1861].

The schema is seventeen documented rows over eight tables, every key optional with the command line's own defaults, so a profile only says what differs; the loader's own key sets give twenty-two leaves, because the verification row bundles four keys and the sleep row two, and the top-level `clients` key ([the driven client](#driven-client)) has no row [#1796].

| Key | Type | Default | What it does |
|---|---|---|---|
| `fixture` | string | `"default"` | The fixture restored; it wins over a typed `--fixture`, the conflict printed |
| `description` | string | `""` | Free text, carried into `report.json["profile"]` |
| `[[mods]]` `id` | string | — | The name in `Mods=`; a harness id resolves to the repo folder, any other bare id through the workshop index |
| `[[mods]]` `workshop_id` | string | — | Resolve from `<WORKSHOP_DIR>/<item>/mods/*`; an item shipping more than one mod needs `id` as well |
| `[[mods]]` `path` | string | — | An explicit folder, absolute or repo-relative: how a mod not on the workshop goes under test |
| `[[mods]]` `copy` | bool | `true` | `false` = named in `Mods=` and placed nowhere; needs an explicit `id` |
| `[sandbox]` | table | `{}` | Top-level `SandboxVars` merged into the restored fixture's file ([the sandbox block](#sandbox)) |
| `[server]` `timeout` | int | `420` | Seconds to wait for `*** SERVER STARTED ****` |
| `[server]` `SleepAllowed` / `SleepNeeded` | bool | the fixture's ini (false, false) | Written into the server ini at seed. A sleep reading needs both true: with either false the server's fatigue reset erased each fatigue write at the next update [#2947/M/n=1, #2948/M/n=1, #2793/C/C-only] |
| `[server]` `gclog` | bool | `false` | Adds `-Xlog:gc*` to the server's JVM, writing `<run>/gc.log`, so a ZGC pause or allocation stall can be lined up with a frame ring [#3408/M/n=1] |
| `[client]` `timeout` | int | `300` | Seconds to wait for a client to reach in-world |
| `[client]` `users` | list | `["admin"]` | The older spelling of the top-level `clients` key, allowed beside it only when the two agree and not checked against the fixture; an empty list is a pre-boot error, since a client-less run is not wired |
| `[client]` `safemode` | bool | `false` | Never set it (the safe-mode rule above) |
| `[client]` `launcher` | `"java"` / `"exe"` | `"java"` | Validated against argparse's own choices |
| `[client_overrides.<user>]` `<ModId>` | string (folder) | — | One attached client gets a different folder for one mod the profile places; the server and every other client keep the profile's source. An unattached user, an unplaced mod, a path that is not a folder, or a folder whose `mod.info` declares another id is a pre-boot error [#3379/C/C-only] |
| `[run]` `hold` | int | `5` | Seconds to hold the session open after `session_ready` |
| `[[verify]]` `side` / `cmd` / `args` / `expect` | array of tables | `[]` | Bus probes run after the client is ready; `side` is `server` (default), `client` or `client:<user>`; `expect` is a string matched as a substring of `json.dumps(parsed ack)` |

The profile's fixture wins over a typed fixture flag, the conflict printed, because the sandbox keys were validated against it; every other typed flag beats the profile, which beats the module defaults, and the two entry points clear five flags' defaults to a null that means not given, because the argument parser cannot report whether a flag was typed [#1797]. The profile mark is the run's first timeline entry and the only place the log says that a later not-found mod was intended; the report grows a profile block, asked for and resolved, and a verification block, while a profile-less run's report keeps exactly its old keys [#1801/M/n=1].
A profile cannot be attached to a running session: the attach command builds a server stub and never installs mods, so the parser rejects the flag [#1812]. Name a mod by its id rather than its workshop item whenever the item ships more than one mod; at least one installed item shipped three in the 2026-09-10 corpus snapshot [#1617/C/snapshot].

A mod entry resolves through six branches in a fixed order, and every miss raises before a process starts, naming the paths it looked at; for the folder and workshop branches the id comes from the folder's own mod-info file, a missing id pointing at the layout lint and a disagreeing one quoted both ways; the order makes an explicit folder beside a workshop id an error rather than a silent drop, and duplicate ids collapse to one name in the mod list [#1799].

| Entry | Source folder | Fails when |
|---|---|---|
| `copy = false` | none | no explicit `id`; `copy` is not a bool; the id is the harness (`PZTestKit`) |
| `path = "…"` | the folder, absolute or repo-relative | not a directory (raw and resolved path quoted); `workshop_id` set as well |
| `workshop_id = "…"` | the item's single `mods/*` folder | not installed; ships more than one mod and no `id` picks one; no folder declares that `id` |
| `id` in `HARNESS_MODS` | `testing/PZTestKit/PZTestKit` | — |
| `id` alone | the workshop index entry | not a harness mod and not installed |
| none of the above | — | always: "needs one of: id, workshop_id, path" |

The harness mod is prepended when a profile does not list it, because without it there is no command bus, no ready marker and no probes [#1800]. A `copy = false` entry is named in the mod list and placed nowhere — the missing-mod path, reproducible with nothing installed — and needs an explicit id, the harness id being refused [#1798]; the client's own mod file still names the skipped id, so both sides walk the same road [#1822].

Placement is a copy because a no-Steam client searches nothing else: every mod a profile names is copied into the per-run cache on both sides from one source map, the workshop-items line written empty and the numeric workshop id kept only as provenance [#1791]. The installer copies harness mods from the repository and everything else from the profile's source map, which wins over both the harness map and the workshop index [#1803]; on the plain path the orchestrator indexes the workshop tree by the id each version-folder mod-info file declares and copies by folder name [#1865].
Every profile mod lands in a folder named for its id, so a run's mods listing shows ids, a convenience of the harness and not a loader requirement [#0836]: both profile branches return a non-empty source, so no profile entry reaches the name-keeping fallback, which belongs to the plain non-profile path [#1804]. Two sessions measured that placement: the listing held the declared id with no folder-named directory, the mod-info file sat under the id folder and the configuration's mod line named the id, and the mod loaded [#1833/M/n=1] [#1453/M/n=1].
So a profile run's mod-folder metadata cannot answer the folder-rename question: the two spellings are one directory on this filesystem, and no profile reaches the folder-name-keeping branch [#1506/C/C-only]. The workshop-items line stays empty because the seeding code writes it from a list no profile fills; the numeric id is provenance in the report, what makes a run re-subscribable and not what makes it load, and the clients' missing-setting warning for the empty value is baselined noise [#1805/C/C-only].
Both sides are seeded from one source map, the client defaulting its sources and skip list to the server's so the two cannot drift; after the acceptance run both mods directories held exactly the two mods, the client's enabled-mods file naming both in the same order [#1823/M/n=1].

Four nets close the missing-mod hole, in cost order, and only the third proves effect rather than arrival [#1818]: pre-boot resolution turns almost every way to get it wrong into an error for the cost of a second; the fail-fast, for the cost of a server boot, runs after the server-started mark and before any client launch, on the plain path too, marking the missing mods, copying up to five server warning lines into the timeline and raising; the verification probes cost the session up to client ready; and the end-of-run net, taken after teardown so the server's closing lines count, costs the whole session. The end-of-run net alone catches a client-side missing mod, because it unions the server's not-found list with every client's where the fail-fast reads the server's alone; it saves the verdict, not the cost [#1819].
The missing-mod run cost 23 seconds wall and exited 1 against the two-mod run's 93 seconds, its timeline running from the profile mark through server launch, server started, mods not found, the copied warning line, an error mark, the server stop and the faults mark, with no client launch phase and no clients directory in the run folder [#1820/M/n=1].

A verification expectation is a substring of the dumped JSON acknowledgement, deliberately forgiving because it matches at any nesting and so cannot express not present or a numeric comparison; a probe that needs either belongs in a scenario with a Python evaluator, and a number is coerced while a boolean is rejected pre-boot [#1828]. A failed verification probe makes the result a named failure, and on a plain run it also skips the hold, because the test slot must not open on a session that is not the one asked for; on a scenario the failure folds into the result after the test, because the time is already spent and the evidence is worth writing [#1829].

<a id="sandbox"></a>
### The sandbox block: what a profile may change on a restored world

The sandbox block merges and does not replace, because a partial options table on a restored fixture would reset every option the world was provisioned with: it rewrites only the named four-space keys in place, keeping the server's comments, the five nested tables and the file's line endings, and that is what survives the server's whole-file rewrite at boot [#1806]. A key that is not a settable option of the restored fixture's own file is a hard error before boot with the three closest names, except on a machine with no fixture cache, where nothing is checked and a typo survives to a run that cannot start anyway [#1810].
A sandbox option set through the live setter applies at once on a running dedicated server with no push, measured on the server side of one fixture and one run [#0556/M/n=1]. A profile's value survives the server's boot-time rewrite: after seed and rewrite the run's copy read the profile's `DayLength` 1 and the fixture's `Zombies` 6, kept 189 four-space assignments, 184 settable options, 45 533 bytes and 1 020 CRLF endings, and differed from the fixture by one hunk of one line [#1807/M/n=1].
Of the 189 four-space lines five are nested-table openers, which is why the settable-option list returns 184, both counts stable across the merge; a profile naming a vanilla nested option or a table opener is rejected rather than silently doing nothing [#2812/M/n=1]. A profile's nested `[sandbox.<Prefix>]` table sets a mod's own option, written in the server's nested shape ([sandbox-options.md](sandbox-options.md#server-file)); the mod's two modes were booted that way on a live server, which a top-level key could not express [#2807/M/n=1].

Five sandbox options carry the nutrition work; all five are settable from a profile and only the day length has been exercised by one [#1809/C/C-only].

| Key | Fixture value | Why it matters | Owner |
|---|---|---|---|
| `Nutrition` | `true` | The one option gating nutrition at all, and it gates only `Nutrition.update()` | [eating-pipeline](../facts/eating-pipeline.md) |
| `FoodRotSpeed` | `3` | Enum 1–5 scaling `age += ΔgameHours × FoodRotSpeed / 24` (3 = ×1.0, the default) | [food-item-model](../facts/food-item-model.md) |
| `FridgeFactor` | `3` | Enum 1–6 scaling aging inside a powered fridge or freezer (3 = ×0.2, the default) | [food-item-model](../facts/food-item-model.md) |
| `StatsDecrease` | `3` | Enum 1–5 on hunger and thirst drain (3 = ×1.0, the default) | [body-and-weight](../facts/body-and-weight.md) |
| `DayLength` | `4` | Real minutes per game day (`1` = 15 min, `4` = 1 h 30 m), the clock every timed scenario is fitted against | [the cadence ceiling](#cadence) |

<a id="driven-client"></a>
### The driven client

A driven client is a Java process started directly, with no launcher and so no elevation prompt, run with no Steam, its own cachedir, no sound, no voice and a connect argument naming the server's address and port, the debug flag added only for the admin account [#1710]. The harness mod must be in the server's mod list, because the client reloads its Lua with the server's list on join; it then reads a join manifest from its cachedir, presses connect and steps through the creation screens, which a restored fixture client skips because the character persists server-side [#1715].
A golden client cachedir is about one megabyte: the options file with the terms flag, the mods folder with the harness, the enabled list and the reset marker, the saved-server database and the join manifest [#1857]. The harness also sets the client's helper-dialog options (the survival guide, the first search tutorial and the first animal-zone info) to false in each client's options file at every prepare, and blanks the server's welcome message at seed. A loaded client sits on a click-to-start screen, because the loading state polls for input before entering the game and nothing in the console or the harness fires until then, so every in-world figure of the join spike means loaded and waiting there [#1859]; the orchestrator posts a click to the client's own window, matched by process id without changing focus, until the harness reports the player's position [#1716], taking a loaded client to a ready player in about two seconds [#1859].
Process-id matching works because the window is owned by the Java process the orchestrator spawns, posted clicks need no focus, the harness survives the join-time Lua reset by recovering the last executed sequence from the acknowledgement file, and the chunk cache is keyed by address and port, so booting a fixture on its recorded port keeps it warm [#1863]. Every copied mod adds baselined noise, a missing-file exception for the optional animation folders it does not ship, and the acceptance runs recorded zero server errors with those lines present [#1827/M/n=1].

The debug flag is session-ending for a driven client: on two independent boots the client reached the in-game state, printed one complete trace and stopped — console dead at the last trace line, ready line never printed, bus never answering, process still alive [#1712/M/n=2]. The route is the debug arm of the Kahlua failure helper, which calls the interface breakpoint before the throw; the breakpoint returns at once on a server, so no server ever breaks, and otherwise enters the modal synchronisation pump [#1713/C/C-only]; what that costs a driver, and what a release client does instead, is [lua-platform](lua-platform.md#debug-break).

Fixture `two` records two accounts, `admin` with the debug flag and `bob` without, written by `pzt provision --name two --clients admin,bob`, and gives `bob` a ready time of 35.3 s at the provision, one reading of a client launched without `-debug` reaching a ready world (n=1) [#3302/C/snapshot]. A driver or a verification row names a client's side `client:<user>`; a bare `client` still means `admin`, and a user the run did not attach is an error naming the attached users [#3303/C/snapshot].
A profile's top-level `clients` key, `["admin"]` by default, lists the provisioned accounts a run attaches, launched one at a time with each ready before the next, and that whole set is one session [#3304/C/snapshot]; the two-client session attached `admin` and then `bob` that way, `bob` ready 40.9 s after its own launch [#3298/M/n=1]. The release client in that session answered the bus, read its debug flags false and its debugger error count 0, and had the mod's tooltip hook installed [#3297/M/n=1], and `event.trigger` addressed to it toggled its own panel [#3296/M/n=1].
On fixture `two` the players spawn at (10720.5, 10195.5) and (10911.5, 10037.5), about 248 tiles apart (arithmetic); there `bob` held no remote player in any frame, while `admin` held `bob` only at whole-tile positions that changed at most once an arm, by a whole-tile jump, with a player-packet stamp every 400 ms at the median [#3493/M/n=1]. RCON `teleport "bob" "admin"` replied an empty string and moved neither player, while `/teleportto` sent from the admin client through `lua.call DebugContextMenu.onTeleportValid` put admin at (10913, 10037) beside `bob`, so a reading that needs the players near each other moves one that way first [#3493/M/n=1].

<a id="bus"></a>
### The command bus

The command bus is a pair of files in each side's cachedir, one protocol on both sides: the orchestrator writes a sequence number, a command and its arguments, the harness executes each sequence once and answers with an ok or error prefix plus a string or one line of JSON, the dedicated server polls from the tick and once-a-minute events, and the last executed sequence is recovered from the acknowledgement file after a Lua reset [#1717]. A result is written as one complete JSON object and that completeness is the ready signal, because the file writer's extension allowlist rules out marker files; the orchestrator collects results into the run report, and a partial write never parses [#1761].
The bus answers with no client attached: a server ping answered in 1.51 seconds, the version control read 1, and all ten echo checks passed, over two boots on the server alone [#0933/M/n=2]. The live registration set, counted on 2026-10-27, is 139 distinct names over 156 registration sites, seventeen names being registered twice, once per side; the generated table counts the sites and not the names [#2808/C/snapshot].
That table, one row per name and side with the arguments, reply keys and purpose, is [`harness-commands.md`](../reference/harness-commands.md), generated from the registration sites.

The test layer answers three commands: a sorted list of registered names; a run command acknowledged as started, unknown, already running with the running name, or a player-resolution error, only started leading to a result document; and a status reply carrying the running flag, name, clock, due minute, side and sample count [#1722]. The bus answers a translation lookup on both sides because the command is registered once in the shared file, which loads before the client file, and a reply tells a Java null return from a translation miss [#0930].
The harness's only string setter is the chef field on an item, the only route from the bus into the cooking-experience branch of the food update, because an admin-command spawn leaves that field null; an empty value is refused, since an empty chef reads as no chef [#1723]. `lua.setpath` is the drivers' setter of a plain Lua field reached by a dotted path from the globals (`globalmoddata.setpath` assigns into a global modData table instead): a server-side, test-only command assigning a true, false, nil, number or string scalar, whose first use flipped a mod flag live and read it back [#3078/M/n=1]. That it never creates a field on a missing parent and carries no role check, the bus being the harness's own file channel that only the driver writes, is the command's own text, its comment block at `repo:testing/PZTestKit/PZTestKit/42/media/lua/server/PZTestKit_Server.lua:2769`, and not a reading. `record.set` sets a scalar in the mod's in-memory record by `lua.read`'s path grammar, so it reaches the bracketed keys a dotted path cannot, every full type holding a dot; that it indexes the store's table directly and never creates a record or a parent is likewise its comment block at `repo:testing/PZTestKit/PZTestKit/42/media/lua/server/PZTestKit_Server.lua:4542`. No chunk runner exists, because `loadstring` is removed on 42.20.x [#1082/C/snapshot].
The client `lua.setpath` and a two-sided `lua.call` worked on first live use: a zero-argument call replied a number on both sides, a two-argument call a table's key count, a missing target `failedAt`, and the client setter wrote and read back its value [#3199/M/n=1]. `event.trigger` and `lua.callm` worked on first live use: a triggered key press ran the mod's own Lua key handler, the reply saying only that the call did not raise [#3265/M/n=1], and a method call reached a panel instance through a numeric path segment and the character-info tab's view through a vanilla global path [#3266/M/n=1].

The harness Lua is eight files split by load order and by which part of the work owns them [#1771]: `shared/PZTestKit_Core.lua` loads first and carries the global table, the key-value files, the encoder, the bus, results and the witness; `shared/PZTestKit_Test.lua` sorts after it by name and carries the test layer (the game-minute scheduler, the registry and the test commands); `server/PZTestKit_Server.lua` polls the bus and answers the server's witness commands; `server/PZTestKit_Server_Recipes.lua` sorts after it, a dot sorting below an underscore, and carries the recipe readers; `server/scenarios/` holds the smoke and nutrition scenario files under a folder the loader walks recursively; and `client/PZTestKit_Client.lua` (auto-join, the client commands, the round-trip comparison) and `client/PZTestKit_Client_Body.lua` (the client mirror's commands) register into the same table, kept apart so two lines of work cannot collide.

### The agent link (Plans 21, 21b and 22, exploratory)

Plan 21 built the link and ran Stage A's first three passes; Plan 21b ran a fourth Stage A pass, two Stage B passes and two Stage C survival runs, and § 7 of the agent harness report (`docs/superpowers/specs/2026-10-26-agent-harness-report.md`) weighs them. The agent link is a client Lua mod, `testing/PZAgent`, run from one `OnTick` hook: it appends JSON lines to `Lua/pzagent/<user>/state.log` in the client's cachedir and polls `cmd.txt` there, taking a command only when its sequence number exceeds the last one taken, which `ack.txt` keeps so a Lua reset never replays a command [#4173]. At its start it writes a probe file twice and counts the lines, writing `state.log` in append mode when it reads two and one chunk file per flush otherwise [#4174].
Append held in all three Stage A sessions, with no sequence gap and no unparseable line; the 60 s windows held 121, 301 and 600 frames at 2, 5 and 10 Hz in the first session and 120, 300 and 601 in the second and third, against 120, 300 and 600 expected, and a 30 s window at 60 Hz held 1803 frames against 1800 [#4175/M/n=3].
The link's measured cost on a tick that builds a frame is about half a millisecond: in the second session every one of 300 frames at 5 Hz read 0, 1 or 2 ms on the 1 ms clock (2 on 33, mean 0.623 ms), so the 99th percentile is known only to lie at or below about 2 ms, and in the third 1803 consecutive frame ticks at 60 Hz summed 869 ms, a mean of 0.4819744869661675 ms [#4176/M/n=2].
A scan's walk costs about 0.016 to 0.018 ms a square [#4177/M/n=2], and writing its line about half a millisecond per KB: the whole line emitted on the completing tick read 7, 19 to 22 and 44 to 45 ms for 16.7, 48.6 and 99.3 KB, and part lines fit 0.495 ms per KB through the origin with a fixed cost of about half a millisecond a line [#4178/M/n=2].
So the scan goes out in 60-square parts, one a tick, and a 15-tile scan of 961 squares in 17 parts cost at most 7 ms on any tick, where a 2 to 3 ms walk step met a 3 to 4 ms part emit [#4179/M/n=1].

### Reading a reply

A subject that does not resolve is a result and not a usage error: both witness commands answer their usual envelope with a false resolved flag and an error, only the first-argument gate answers a bare string, and a third gate inside the table branch answers a table whose error begins with the usage word, so a driver checks the error before trusting the fields, a type check being necessary and not sufficient [#1748]. The resolved field names the subject that answered, not the one asked for: for an item the owner, full type and id; on a client always the local player, whatever user was sent; and the global scope sets it at all, having no subject [#1749].
A getter has three outcomes — not exposed, exposed and raised, or answered nothing — in three lists, each getter under its own protected call so a wrong-arity dispatch costs one key and not the reply; the middle bucket exists for one overloaded getter, and all three lists came back empty on all fifteen probes of one session [#1736]. The global walk takes a hop only when the node is a table, so a non-table node ends it and the reply names the segment and the type that stopped it; the key count is gated the same way because iterating a Java-backed object raises; presence is a nil test, so a global that is false or minus one reads as present; and on a build with no global table the reply carries no failed segment, which a reader must treat as that case [#1759].
The modData witness differs here: its dotted walk turns a false leaf into nil, so a nested false boolean is listed under `missing`, while the same boolean inside a table read whole comes back false [#2990/M/n=1]. A false resolved flag from the global walk means this path and not this mod, the two being the same claim only when the name is known to exist in one copy of a file and not another, which is why the harness's own version global is sent first as the control, and it must answer on both sides [#1760].
One side answering a script read is not evidence about the other, because script data loads per side and is never synced, though both sides run the same implementation and the reply names its side [#1724].

The translation read answers in four shapes: a hit, a miss that returns the key itself, a Java null reported as a miss with a null flag and no text, and a usage string when no key is given [#1718]; what a dedicated server's translation route answers is [`mod-anatomy.md`](mod-anatomy.md). Two non-finite cases still answer null on the bus, because JSON has no literal for either and a bare one would lose the whole acknowledgement rather than one number [#1755/C/inference].

Seven vanilla noise signatures are allowlisted, four surfacing only once the big three were filtered, and with all of them in place a clean vanilla boot scores zero, so any nonzero count is a real finding [#1850]. The error classifier over-counts first by harness echo: no echo pattern is whitelisted, so a reply carrying exception text is filed as a fault, and a session reporting four server errors was four verbatim echoes of the driver's own reading and zero engine faults [#1765/M/n=1].
It over-counts second by counting engine output per line: one Lua error contributes ten entries — four error-message heads, four bare stack-trace lines and two exception lines — so a session reporting 892 error lines is about 89 fires and not 892 events [#1766/M/n=1].

The nutrition setter's acknowledgement carries the weight-direction flags one tick stale: the acknowledgement of a calorie write reads the increase flag false beside the new calorie value, because the weight update has not run again yet [#1492/M/n=1]. A container reading is presence and within-side stability only: the leading type token agreed on both sides while the full strings differed exactly where the jar says they must, the string ending in the parent object's per-JVM identity hash, so comparing the strings across sides reads as a desync and is not one [#1507/C/n=1].

### Probe design

For anything the server owns the client's reply is a mirror, so a probe's first decision is which side to ask [#1826]. Aging must be read on the server: an age probe on a client measures the client's stale copy, which is the finding rather than the number [#0359/M/n=1].
Every intake probe is server-side because a multiplayer client never calls the drink routine: the net timed action skips the Lua completion on a client, so a client probe would read the once-a-second mirror rather than the store [#1729]. A server-only script census is the whole answer, because a client census would count the same load-time objects [#0647/C/inference].
Every rate in the body model was fitted server-side, the client mirror read only at session start, at the idle baseline's boundaries and in the two client-write probes, so nothing there bounds the mirror between those points [#0573/M/one-side].

Exclude the custom name and the tooltip from any item-modData census, because vanilla writes both into item modData and a census that keeps them reports vanilla as a finding [#1043/M/n=1]; the client's copy carries the custom-name key because the deserialisation path writes it into modData [#1753/M/n=1]. Every item-modData reading names the side it was taken on, and a probe that writes one key on the client and transmits rewrites the server's copy of every other key on that character [#1640/M/n=1].
A player census excludes the four vanilla fitness keys and the hotbar instead, and is taken late in a session, because the server's copy of a player's modData is empty at join and holds four keys only about half a minute in [#1966/M/n=1]. The server-side player modData setter exists because the player census is four keys on the server against five on the client, a strict superset, so without a planted server-only key the difference set that would expose the receiving side's wipe-before-write is empty [#1757].
A pure client-interface mod's persistent state is invisible to the bus until a human clicks: one mod's configuration key was absent on both sides at all six snapshots and its six probed leaves were read once per side, because all seven writers are input handlers and on that session's harness no bus command could synthesise a click or a key press; the test-only `event.trigger` now fires a Lua-side key event, and a physical click or key press is still not synthesised [#1498/M/n=1].

The item census is the game's own loaded-item list bucketed by the raw item-type string, counted raw so a registry rename shows rather than silently zeroing, and it is the live cross-check for the script-side food scanner [#1726]. A live fluid census must pair the fluid-type string getter with the enum getter to be exhaustive [#0655/M/n=2]: the string getter answers for only 34 of the 61 definitions, empty for every fluid that also has a built-in enum constant, so the command falls back to stringifying the enum and reports which route named the fluid [#1727].
The fluid read lists all sixteen members it asks for — the fourteen property getters plus the display name and the properties-set test — of which ten read the flag false on this build [#1725].

The drink probe picks the fullest container, ties broken by the highest id, because the first-match finder would re-select an already-drained can on a second probe of the same type; the candidates, the pick and the route that answered travel in the reply [#1730]. It is drift-free by construction: both snapshots are taken inside one Lua call on either side of the single Java line, the same game tick, and the world age before, after and its delta travel in the reply so that is checked rather than asserted, while a bracket around the command is the outer reading and does carry the passive drain [#1731].
A container's aggregate properties are read before the drink, because an emptied container recalculates to all zeroes [#1732]. The item-use command consumes uses as a craft input line without an item-count flag does and skips the bookkeeping after the reduction — the replace-on-use spawn, the client push and the removal — so a fully consumed item stays in the inventory, and the reply says which of the two happened [#1738].
It refuses an instance already at zero uses and answers the before snapshot unchanged, because a depleted food has no hunger change and the setter would write a not-a-number factor into every macro [#1739].

A bare recipe name and its module-qualified spelling both answer, craft and evolved alike, but only for a recipe declared in the base module: one declared in another module answers to neither, because both still land in the base module, and all fifteen probes behind that reading were base-module recipes [#1734/M/n=1]. The craft-recipe read tries a third route only after both spellings miss, a walk over every loaded craft recipe matching the last dotted segment of the cached full type and falling back to the plain name, so a bare non-base name answers and the resolution rule stays measured; a caller who wants the rule exercised asks module-qualified [#1735].
The global-walk command walks the Lua global table segment by segment and never calls what it finds: a function reports the string function, because reading its result would mean calling an unknown global at unknown arity, and an unguarded one aborts the rest of the handler body and on a debug client parks the process [#1758]. The `store.probe` text helper formats a nonzero number of tiny magnitude with `tostring`, because Kahlua's `%g` has no exit for such a magnitude and a `pcall` cannot catch the freeze; `tools/kahlua_lint.py` flags a `%g` format unless its line carries the allow pragma [#3764/C/C-only] [#3763/M/n=1].

<a id="witness"></a>
### The witness contract

Both reflective witness commands are registered in the shared harness file, so both sides answer them and every reply says which side did: one generic command instead of a getter-specific one per mod, so no per-mod Lua is written before these two have been tried, and a name reported missing means the build does not expose the member, which a per-mod comparator would have died on [#1741]. Each name a field witness is asked for lands in exactly one bucket: missing means the object does not expose the member, nils means it is exposed and returned nil, a reading rather than an absence, and fields is everything else, so the mod did not set it and this build never had it are different answers; the guard indexes before it calls, because a caught nil call names no member [#1743].
Every modData witness reply carries the census, every top-level key as a sorted name-and-type list, so a wildcard or no key is a valid call and is how a mod's modData shape is discovered; a dotted path walks nested tables, a path that does not resolve is reported missing exactly as an unset key is, and the read count and the census size stay separate numbers [#1745]. The three scope words are reserved in the modData witness's first argument, bare and with a trailing colon, so a key literally named after a scope is asked for behind an explicit prefix; the gate is a lookup table because Lua patterns have no alternation [#1746].
A witness call reads at most 32 names, both replies travelling as one acknowledgement line, and the cap is counted before the read, so the count is what was read and a truncation marker is the only signal that more were asked for [#1747]. Both witness commands answered on both sides for a player and an item in one session, fifteen graded rows over seventeen probes — fourteen as expected, one finding, no misses — and no truncation, so the cap never bit; the command shapes are structural, but every item number and the modData asymmetry are single readings that support no always claim without a second run [#1752/M/n=1].
The maximum carry weight read 12 on both sides at all six snapshots of one session and matched the body snapshot's own field on both sides, which proves the harness's Java-member call wrapper sound [#1500/M/n=1]. The three weight-direction flags are read-only keys on the nutrition snapshot, in every nutrition and stats reply on both sides and omitted on a build without them; they are not in the player-stats packet, so the pair of readings is the only way to see whether a client recomputes them from its mirrored macros [#1756].
Every sample is stamped with the game minute, the world age and the wall clock, and the world-age-and-wall pair is what the Python side fits rates against, which makes the harness's cadence measurable without a second round trip; the world-age read is guarded, so a build that lacks it just omits the key [#1778]. The older round-trip witness is a different instrument and still exists beside these two: its modData command carries a name of its own, while the kind on the wire, the comparison and the result file name are unchanged, and its nutrition and item witnesses are untouched [#1874].

<a id="scenarios"></a>
### Scenarios and the test layer

A scenario is a Lua test that runs on the world's own clock — days of game time in minutes of wall time — and hands its samples to a Python evaluator [#1772]. A registered test carries a backstop in game minutes, a subject username, a needs-player flag and a run function; clearing the needs-player flag is the only way to register a test with no subject [#1773].
Leave the backstop a clear margin above the finisher: it is armed first, so it holds the lowest sequence number and wins a same-minute tie, and a test finishing at exactly the backstop minute is timed out with an anonymous detail; the shipped nutrition scenarios finish one minute past their run length with the backstop 29 game-minutes above that, and the smoke test finishes at twenty with a backstop of thirty [#1774]. The test context offers a schedule-once call, a repeating call re-armed before its callback runs so one raising callback cannot stop a multi-day sampler, a predicate poller under its own protected call that ends the test with a labelled timeout, two assertion helpers, a sample appender and a finisher whose pass flag is combined with whether any failure was recorded; that protected call catches ordinary Lua errors and not a call to a Java member the build lacks [#1777].
Every Java member in the test layer goes through the guarded call, because an unguarded nil call aborts the rest of the once-a-minute body it fires in; the handlers behind it still run, and a protected call catches it but names nothing [#1781]. The scenario subject is resolved by username from the online-player list, because a dedicated server has no single-player getter, so the client must be attached even for a server-side test; the fallback is the run argument, then the test's own player, then the admin account [#1779].

Three scenarios ship, all server-side because the server owns nutrition: a scheduler self-test of about twenty game minutes asserting only that the clock ran, samples landed and one predicate poll reached a hit, and two three-game-day nutrition runs, one at four thousand calories a game day fed as two doses twelve game-hours apart under the calorie clamp and one at no intake, both sampled hourly with hunger and thirst pinned to zero after every sample [#1782]. The nutrition scenarios record the server's nutrition object once a game-hour, and the evaluator integrates the weight model sample-to-sample over each run's own calorie and macro trace, passing when its predicted weight is within the greater of fifteen per cent of the predicted delta and 0.05 kilograms of the weight the server reported [#0157].
An evaluator is a Python function keyed by scenario name, registered by importing its module; a name with no evaluator passes on the harness verdict alone, and the nutrition evaluator fails the run outright if any sample is dead [#1786]. The runner refuses a name the chosen side does not report and any run acknowledgement other than started rather than paying the full result timeout, and a refused time-speed command ends the run with that reason, since a three-game-day test at real time could not finish; an interrupt is caught, tearing down as usual and still writing the report and artifact [#1783].
A scenario runs the Python evaluator before it restores the time multiplier, because the evaluator is scenario code that can raise and a raise must not skip the speed restore, which sits in a cleanup block so a world change cannot outlive the run; the order is boot and attach, `test.list`, RCON `settimespeed <N>`, `test.run <name> <user>`, the result doc, the evaluator, then `settimespeed 1` and teardown, and the artifact, written last, carries the profile and the probe results on every run, null and empty when there was no profile [#1704].

<a id="cadence"></a>
### The cadence ceiling

The scheduler's clock is game minutes and not wall seconds: the game's once-a-minute event advances it and dispatches every callback whose minute has come, sorted by minute and then insertion order, the layer carrying its own sequence because the sort is not stable [#1775]. The scheduler hooks that event once, because a reload re-runs the file and a second registration would advance the clock twice a game minute and halve every rate fitted against it [#1974].
The once-a-minute event fired at exactly one tick per game minute on the dedicated server at a time multiplier of thirty on all three of one set of runs, at the fixture's four-unit day length, which is what makes it eight game-minutes of world clock per wall second, a ratio that is not a property of the speed flag alone [#1776/M/n=3]. Each of those three three-day runs took 73 hourly samples over 72.0 game-hours at a multiplier of thirty with no server error lines, the event ticking 1.000 times per game-minute at 7.99 to 8.00 game-minutes per wall second [#0156/M/one-fixture].
Every run fits the harness clock against the world clock and the wall clock, and a tick rate outside 0.95 to 1.05 per game minute sets a suspect flag and a warning: the run still reports, but everything scheduled in game minutes and every rate fitted per game-hour was read off a clock that was not keeping time, the usual cause being the day length combined with the speed flag, not the speed flag alone [#1787]. A fifteen-minute day at a multiplier of thirty overruns the scheduler: the run recorded 0.22 ticks per game minute with the suspect flag set, the event firing twenty times while the world advanced 91.05 game minutes, and its self-test still passed because every assertion it makes is counted in ticks, so nothing fitted against the game clock on that run may be cited [#1813/M/n=1].
The ceiling holds on the fifteen-minute day as on the ninety-minute one: at a multiplier of five, the same arithmetic value of eight, the run recorded 7.57 world-minutes per wall second and 1.018 ticks per game minute with no suspect flag [#1816/M/n=1]. The dedicated server's inventory-item tick runs about once every 5 s rather than every frame, because the time-multiplier calculation's server arm is real-time-delta driven and clamped at 6 s, so a bus call cannot be made the cause of a server-side item transition at this time multiplier [#1113/M/n=2]; a bus call cannot win a race against that tick, and a probe must not assume per-frame item updates [#1420/M/n=2].

<a id="time"></a>
### Game time against real time

One game minute is 3.75 real seconds at the fixture's day length of four, which is a 90-minute game day of 5400 seconds over 1440 game minutes [#0893/C/arith.]. The measured body run ran on a fixture whose clock was 16.027 game-seconds per real second, that same ninety-minute day, and every rate was fitted as a least-squares slope against the world age read from the same snapshot, so the speed setting cancels and the accelerated windows are directly comparable with the baseline [#0452/M/one-fixture].
Boot cost is not constant within a session: the first boot cost 36.6 seconds against 13.7 and 14.0 on the same session, a gap measured while its cause is not, the first boot of the session being the suspected reason [#1846/M/n=1].

<a id="artifacts-discipline"></a>
### Artifact discipline

Every invocation writes its own run directory holding the server log, the server and per-client cachedirs and a report of timeline and events, a timeline mark being a seconds-since-start stamp plus a phase, and a step that measured its own cost adds a separate duration field [#1706]. Every result document carries the same envelope beside its own keys — its name, the side, a wall-clock timestamp at write and a completion flag — and the timestamp is load-bearing, because with the start stamp it is the pair the cadence fit uses, so a side with no millisecond clock produces no cadence block [#1780].
Two shapes in the committed reports are traps. A mark's observed value is truncated at 100 characters, which on the acceptance run stops immediately before the value every took-effect claim rests on, so quote the parsed verification block and never the mark [#1794/M/n=1]. The elapsed field on the server-started and client-ready marks is that step's own duration, not elapsed time, in every artifact committed before the harness passed the duration separately, so a client ready at 37.3 seconds is a 37.3-second client boot on a run that reached in-world at about 74 [#1795/M/n=1].

The bus number format is a rendering property and not a measurement one: integers take the integral branch with its own cut-off, no key changes name or type, and the current path round-trips a non-integral double exactly where the older one quantised every float to six decimals [#1754]. No bit-level claim may rest on an artifact written before the harness commit `291f977`: its encoder rendered every non-integral number at six decimals, so a cross-side comparison from such a run is equal at the bus's resolution and never bit-equal, the one-in-a-million tolerance the graded rows used being exactly that resolution [#1965]; two teardown sessions measured under that limit stay exactly as recorded, every desync graded on them whole-value and far above the tolerance [#1435/M/n=1].
Give a run id a prefix with no hyphen: the run-id form the checker reads is a lower-case alphanumeric prefix, a hyphen, eight digits, a hyphen and six digits, so a hyphenated prefix is refused; this form is stated in `tools/claimslib.py` and in no register row.
The three scenario artifacts, as the tree stood on 2026-09-10, predate the thirst sample column and the evaluator's dead-subject verdict, neither exercised live, while the scenario's own die-early abort was in place for the second and third runs and never fired [#0171/C/snapshot]. The measured lifecycle run's artifact carries no fixture or build key of its own, which is known only from the fixture file [#0385/M/one-fixture].

A driver is frozen once its run is committed, so a do-not-cite key is a permanent property of its artifact. The drink probe's overall match flag is not evidence about the fluid arithmetic: all 54 fields of the primary drift-free reading matched, and the three flagged rows are the outer bracket's calorie row on each drink, short of its band by 0.002 to 0.008 kcal because the band assumes an exactly proportional idle burn — cite the `atomic` and `container` blocks [#0661/M/n=3].
The craft comparison's overall match flag is not evidence about the scanner: both run-time misses are the same field on two recipes, at 10 against 9 and at 3 against 2, and neither side lost an input [#0761/M/n=10]. The salad observation flags are not evidence that the expansion is wrong: the number they were written against is the wrong number, and an expansion that reproduces the game must include the two drainables [#0765/M/n=2].

<a id="driver-rules"></a>
### Driver discipline

A driver's own timeline is a reading about the driver and not about the engine, and it is graded that way; the repository's live-run rules and the incidents behind them are [process lessons](../process/lessons.md#live-runs). A tag name in a driver's timeline is nominal, not a clock reading: the snapshot named three seconds after a transmit opened 7.58 s after it because the previous snapshot took 7.58 s to walk both sides, and the 1.78 s cross-side read skew at that tag is pure latency, since nothing in a modData census decays [#1341/M/n=1].
A snapshot inside a write's push window is an arrival-latency reading by rule and is reported ungraded, and the two tags nominally three seconds after a write sat at 7.35 and 7.85 seconds because the poll and the snapshot already exceed the settle sleep, so the grading uses each snapshot's own time since the last write [#1488/M/n=1]. Put every negative a run establishes into the artifact's own output: one driver held the not-found mod lists on its server and client objects and never wrote them, so that artifact cannot say no mod failed to load [#1707].
Keep a dormant fallback's routing table as wide as the commands that can reach it: one driver's probe fallback mapped only the two witness commands onto a result-document name although the probe carried three more, so a fire on one of those would block on the wrong document [#1709]. A probe that deliberately raises always makes a run report failure, because the exit code needs zero non-baseline server errors; that is the harness working, so the run is kept and the grading comes off the artifact [#1767/M/n=1].
An admin-command spawn can return an empty reply for an item that did spawn — once in the census run and twice in the drink probe — so both of those drivers key spawn success on a server-side read-back rather than on the echo [#0675/M/n=3]. Every store the drink probe read was taken through the server bus, the client attached only so that the player exists, which leaves the client side of the drink path unmeasured [#0650/M/one-side].

## Walls and bounds
<a id="walls"></a>

Every reading in this library was taken on one fixture with one admin character at a day-length setting of four, under a bus cadence ceiling of about 8 readings per game minute, and most measured rows are one session [#1253/C/one-fixture]. A `-debug` client is stopped dead by the first mod Lua error reaching `KahluaUtil.fail` and parks in `UIManager.debugBreakpoint`'s modal pump, so a raising mod cannot be driven on it; a release client launched once on the two-client fixture answered the bus with its debug calls false and its debugger error count 0 [#3297/M/n=1], and a release client raised on once did not park but answered through the raise [#3317/M/n=1] [#0958/M/n=1] while the -debug client beside it parked [#3318/M/n=1], which is why every raising probe is gated on the server and the client timeout set low [#1246/M/n=2].
Every client-side reading of the unguarded-raise session is unusable: the debug client parked in the Lua debugger and its bus never answered, so that session is a server-VM reading only [#0869/M/n=2]. The server error count is a classifier's output and not a fault count, and a run reporting failure on a raising probe is the profile working as designed: no count of trace blocks is evidence of a fault [#1247].
Nothing on the bus executes a craft: the recipe command is a reader and nothing on the bus reaches a right-click, so a recipe's create and test hooks and the create event stay read from code, the create event never having fired in this library [#1248/C/C-only]. The dispatch case of a protected call and an unguarded raise was measured only inside once-a-minute handlers on the server VM, when the bus had no trigger-event command; the test-only `event.trigger` now fires a Lua-side event from the bus and ran a key handler on each of two triggers without a raise inside it, so what a protected call and an unguarded raise do inside any other dispatch, and whether another mod's protected-call fork around one changes it, is still unmeasured [#1249/M/n=1] [#3265/M/n=1].
The translation session carried no in-run positive control: every reply missed, so the item-name routing claim leans on an earlier session's client-side interface-key hit on a different harness shape, and every later session that calls the translation command must ship a control that hits [#1250/M/one-side]. The translation command's null guard has never fired in a committed run, zero replies carrying the null flag across both sessions that could have triggered it, so the branch is untriggered and nothing confirms its behaviour [#1721/M/n=2]; that it holds is an assumption about the harness, which is why every translation reading of the overrides session is on that run's do-not-cite list [#1251].
`player.stop` cannot cancel a timed action that has started: on 42.20.4 it cleared the queue through vanilla `clearQueue`, which force-cancels only actions not yet started, so an eat stopped about 2 s after it was queued ran to completion on the server in the boot whose wrappers did not cycle, and the vanilla call that stops a started action, `IsoGameCharacter.StopAllActionQueue`, was on no command [#2834/M/n=2]. `IsoGameCharacter.StartAction` clears the character's action stack and pushes the new action without calling `stop()` on the action it removes, while `StopAllActionQueue` calls `stop()` on a started first action, or `interruptWaitToStart` on one not yet started, before it clears the stack; vanilla's `ISTimedActionQueue.clear` calls `StopAllActionQueue` and then the queue's `clearQueue`, whose `cancelQueue` force-cancels only the actions not yet started [#3724/C/C-only].
So a started Fitness set is orphaned when the client's queue is cleared and another action starts: in the worked example played live, `player.stop` followed by `player.walk` left the server's exercise flag set for 44.564151763916016 game minutes, 45 flagged ring rows, up to the client's last online row and past the set's own 20-minute ask, while the character never moved, every one of the 45 drains after the stop billed squats' `3`, and the record stayed squats with no fallback [#3734/M/n=1]. The harness's `action.cancel` closes that wall: it calls vanilla's `ISTimedActionQueue.clear` on the client, and played live it stopped a started squats set and a started eat on the server [#3789/M/n=1] [#1299/M].
The asleep hold re-asserts a connected player's server-side asleep flag once per tick: the flag read set at every in-hold sample (12 of 14 reads; the last two fell after the hold), but about 15 % of stat updates still run awake because the client's reset lands between the re-assert and the update (x132r), and the client's own copy reads awake; the run command only walks, setting the running and path-find running flags while the server read running false at every read of a 30 s run window [#2840/M/n=2]. The field witness reads zero-argument getters only and caps at 32 fields, so the nutrition macros are read through the nutrition command rather than the witness [#1252].
The harness cannot read another player's character from a client: its client-side subject is always the local player, so what a second client's copy of a player holds after a push stays unmeasured [#3292/C/C-only]. Neither script-side command can return a per-item macro and no third one could: the food script object exposes no macro getter to Kahlua, so the live macro read-back goes through a spawned instance; fluid containers have no live route at all, the script item exposing no component accessor, so only fluid definitions can be read back from the bus [#1728].
A global-scope modData census proves less than it looks: the read goes through a get-or-create static that creates the table when absent, so it can never report no such table, and an empty census says only that nothing stores anything under that name [#1750]. The client side of the scenario runner is wired end to end and has nothing to run: the test layer is shared and both bus commands answer on the client, but every registered scenario lives under the server folder because the server owns nutrition [#1784].
Artifacts older than commit `291f977` render every non-integral number at six decimal places, so no bit-level claim may rest on them [#1254/C/snapshot]. An option the world generator consumed once is not retroactive: the zombie population, the spawn regions and the start date belong to the world and not to the boot, so a world-generation option is changed by re-provisioning a fresh fixture; only the day length has been measured on a restored world, so the other four are unproven rather than shown non-retroactive [#1811/C/inference].
A vanilla nested option of the server's file stays out of scope and a profile naming one fails validation [#2811]; a mod's own nested options are the `[sandbox.<Prefix>]` table above [#2807/M/n=1]. The one measurement of the once-a-minute event's own ceiling is 10.08 ticks per wall second, on the run that overran, and where the true ceiling sits between eight and 10.08 is unmeasured [#1815/M/n=1/open].
A case-only folder subject can never answer the rename question: the filesystem is case-preserving so the listing shows which spelling was written, but path lookup is case-insensitive, so such a mod loads whichever name is used, and the regression subject has to differ from its id by more than case [#1834]. The counterfactual is out of reach from a profile rather than merely un-run: both profile branches return a non-empty source, so a mod left under its folder name in the run's mods directory would need it in the golden fixture's own mod list, a fixture re-provision and shared state [#1835].
Two legs of the experiment map are stated but not yet measured, the Lua drink-driver path and a deliberate client/server script mismatch, while modData persistence across a save and reload is measured by run x131p-20261004-192310 [#1255/C/C-only]. The frame ring and the engine's own frame counter agree within 2 ms at the 99th percentile: per statistics window the engine's `max-update-period` and the ring's largest `OnTick`-to-`OnTick` gap differed by p99 2 ms idle and under a burst of eighteen ghost records, so the engine's figure is the hitch reading and the ring attributes it [#3403/M/n=1] [#3443/C/inference].
The idle baseline a frame reading is taken against is short and regular: with two players and the mod's own drain the frame's busy time read p50 1, p99 9 and max 13 ms over 1207 frames, and the start-to-start period p50 100 and max 104 ms [#3404/M/n=1]. The ghost load ran 3474 runs of eighteen ghost records in 193 minute events with 0 failures and no ghost key in the mod's store, and `ghost.stop` cleared the 45 per-username entries the ghosts had left; its starvation count of 0 is trivial under a burst [#3407/M/n=1].
A ghost's minute costs 0.778 of a real player's unfed and 0.978 fed: over forty interleaved pairs at `ghost.load 20` the ghost half took 35 ms against the real half's 45 unfed, and 45 against 46 with each ghost's fast-tier input pointed at its carrier's (`feed`), each record run at most once a minute event and never at a zero time step, so a load that stands in for players is fed, and forty pairs at the 1 ms clock resolve the ratio only coarsely [#3455/C/inference] [#3466/M/n=1]. A ghost restores its carrier's vanilla macro stores after each run, because it shares the carrier with the real player and its weight step would otherwise land every rise on the real player's reconcile [#3754/M/n=1] [#3748/M/n=1].
The `gclog` key's log of one session held 128 ZGC pause lines, the largest 0.12 ms, and 18 allocation stalls, all at boot [#3408/M/n=1]. The engine's `avg-update-period` is no mean of the frame period, being set each frame to about a 21st of it, while `max-update-period` and `min-update-period` are each window's extremes, so a driver reads the extremes and never the average [#3409/C/C-only] [#3443/C/inference].

The design's own risk register names seven risks and what is done about each [#1844]: client windows on a desktop with no true headless mode (`-nosound -novoip`, a small window, never `-safemode`, an unlocked Windows session, CI running L0–L2 only); first-join interface screens (a golden fixture with pre-created accounts and characters, a Lua fallback for the rare reset); timing races (every step `eventually(pred, budget)`, no sleeps, the world-ready barrier a handshake); game and mod updates (the run pins the build, the harness self-reports versions, a `smoke` suite after every Steam update); port and cachedir collisions (a unique run id, distinct ports, teardown verifying process exit); the no-Steam workshop gap (the profile builder copies every mod into the run cache on both sides from one source map, since both workshop roots are gated on Steam mode, there is no server `-modfolders`, and `WorkshopItems=` needs Steam and is written empty); and time acceleration in multiplayer (only in L2/L3 with an explicit multiplier, nutrition tests asserting against game-seconds).

Not covered: a Linux dedicated-server image or any continuous-integration host, a second client's copy of another player, a client-side scenario, a save-and-reload cycle beyond the persistence readings of [server-lifecycle.md](server-lifecycle.md#global-moddata), and any reading of the game through a channel other than this harness — every number on this page was taken on one Windows machine driving one dedicated server and at most one debug client, with one release client beside it in the two-client session.

## Open

- Which sandbox options survive a restore is open: only the day length has been set by a profile on a restored world and measured to apply, and the other four keys the mod work cares about are unexercised; a profiled run that sets each on a restored world and reads it back settles it [#1830/C/C-only/open].

- That a bus reply carrying the null flag is inconclusive rather than a miss — the lookup route answered nothing, where a miss returns the key itself — is unverified: the guard has never fired across the two sessions that could have triggered it; a session shipping a key known to return a Java null settles it [#0931/M/n=2/unverified].
- Decision: whether the mod's own timed tests run on the fixture's day length or a shorter one — the cadence ceiling binds the day length and the speed together, and its upper bound is open (see Walls and bounds).
- Decision: whether the mod's load-time checks are verification probes or scenarios — an expectation is a substring and cannot express absence or a numeric comparison, while a scenario carries an evaluator (see the profile section).
- Decision: which side every test the mod ships reads — the server's reading is the measurement for what it owns and the client's a mirror, so a test that reads the client tests the mirror (see probe design).

## Procedure
<a id="procedure"></a>

The doctor command is the cold-start gate before any boot: it reports a stray game Java process and never kills it, checks three ports are free (counting only listening and established local sockets, so a lingering closed connection does not false-fail it), checks the fixture is present and build-matched, the workshop index reachable and the test runner available, and exits 1 on a failure [#1703].
`pzt run`, `pzt provision` and `pzt scenario` lint every `path=` mod folder with the layout lint before they seed a fixture and stop on an ERROR, so a malformed mod folder never reaches a boot [#3311/C/inference].
A release profile boots the staged copy: `python tools/release_pack.py stage mod/NutritionRevamp --out release` runs first and the profile's `path=` names the staged folder, so the bytes a server would download are the bytes under test, the folder the tool wrote held every file equal to its repository twin [#3315/M/n=1], and the `x20-release` session attached `admin` and then the release client `bob` to that staged build, all three sides reading the mod's version `1.0.0` and build `42.20.4` [#3316/M/n=1].

What a reading costs depends on which of five layers it needs, and every layer's failure is a hard fail of the run; the names are the design's own, with the cost and host it gives each [#1842]: L0 static, lint and parse checks (`luacheck`/LuaLS stubs, the script-DSL parse, the `mod.info` and layout lint), seconds on CI; L1 boot, the server booting with the mod to a clean console — no Lua errors, no checksum or definition mismatch — and shutting down cleanly, about a minute on CI; L2 server sim, harness-server Lua scenarios at accelerated time asserting through a JSON spool, minutes on CI; L3 e2e, one or two real clients executing scripted player actions against authoritative server state, minutes, local; and L4 sync, a client reporting its view for the server to diff against authority, riding on L3.

1. **Profile.** Write `testing/profiles/<name>.toml`: the fixture, the hold, the mods in load order with the harness first, the sandbox overrides, and verification rows certain to pass if the mod loaded at all.
2. **Harness, if the reading needs a command that does not exist.** Land the Lua change in its own commit before the session, with the balance check and the regenerated command table; the next acceptance run is its smoke test.
3. **Scenario, if the reading is a rate.** Register it under `server/scenarios/` with a backstop a clear margin above its finisher, sample on the game-minute scheduler, write an evaluator keyed by its name, and check `24 × speed / day_minutes` against the ceiling before choosing the speed.
4. **Driver, if the reading is a sequence of probes.** Copy `testing/experiments/_template.py`, keep the provenance block, take paired reads client-first at every tag, bracket every read with its own wall offsets, assert a declared field count per read, and write predictions, observations and verdicts in the four-word vocabulary.
5. **Run.** `python testing/pzt doctor`, then `python testing/pzt run --profile <name>` or `python testing/pzt scenario <test> --profile <name>`. A failed verification probe means the session was not the one asked for; a two-client profile runs under the same command as one session.
6. **Evidence.** Copy the artifact into `testing/artifacts/<run-id>/` byte-identical with its row and its do-not-cite table, never edit the driver afterwards, grade every reading off the artifact, and write a trivial, unmeasured or falsified reading as such. The live-run rules are [CLAUDE.md § 5](../../CLAUDE.md) and their incidents [process lessons](../process/lessons.md#live-runs).
